# BruhaNet bot

Telegram-бот продажи VPN-подписок (панель Remnawave). Оплата — ручной перевод на карту, подтверждает админ.
Переписка старого бота (`tmp/*.go`, пакет `tgbot`, в git не попадает — `.gitignore: tmp/`). Старый код — эталон поведения и текстов, не архитектуры.

## Флоу оплаты

1. `/start` или любое сообщение → приветствие + главная клавиатура (Информация / Оплатить / Подписка (copy URL) / Поддержка; без юзера в панели — только «Купить»).
2. «Оплатить»/«Продлить» → клавиатура тарифов из настроек (`Content.Settings`, дефолт — env `PAYMENT_PRICES`; месяцы → ₽, по 2 в ряд).
3. Выбор тарифа → «Верно?» Да/Нет.
4. «Да» → `CreateUser` в Remnawave (если нет; `expireAt=now`). Если у юзера уже есть `pending`-платёж — он становится `cancelled`, юзеру откатывается срок (`PrevExpireAt`), старое админ-сообщение закрывается. Новый платёж — строка `payments` со статусом `pending` (`telegram_id, username, months, price, prev_expire_at` = текущий срок юзера). Показать реквизиты (телефон, банк, комментарии «На кофе»/… — из настроек, дефолты `PAYMENT_PHONE`/`PAYMENT_BANK`).
5. Юзер шлёт фото при наличии pending → фото копируется админу + сообщение с кнопками Подтвердить/Отклонить (в callback `adm_ok`/`adm_no` — **id платежа**).
6. Аванс: `max(now, PrevExpireAt) + AdvanceHours` (настройка, дефолт 24 ч), платёж помечается `advance_granted`. Юзеру — «фото на проверке, доступ на 1 день» (при исчерпанном лимите — без строки про доступ).
7. Админ (кнопки в боте или панель): **Подтвердить** → `max(PrevExpireAt, now) + Month*30d`; **Отклонить** → вернуть `PrevExpireAt`. Оба: статус `confirmed`/`declined`, убрать клавиатуру, реакция 👍/👎, уведомить юзера.

Инварианты: платёж живёт в Postgres (`payments`, не более одного `pending` на юзера — частичный unique index; статусы ровно `pending|confirmed|declined|cancelled`). Решение админа — одна функция на бота и панель, `core/payflow.Resolve` поверх `Store.ResolvePayment` под блокировкой строки: в той же транзакции вызывается `UpdateUser` (ошибка панели откатывает транзакцию, повтор считает ту же дату) и кладётся `payment_result` в outbox (`TextKey` + `ExpireAt`; текст и главную клавиатуру рендерит воркер при доставке, `routes.PaymentNotice`, у api их нет); из панели (`AdminID` в `Decision`) там же — `payment_admin_closed`: воркер снимает кнопки и ставит реакцию у `admin_message_id` и считает бизнес-метрики, сбой не отменяет платёж. Обратно: решённый в боте платёж панель видит при перезагрузке. Повторное нажатие → «Уже обработано», нет платежа → «Платёж устарел». FSM при решении из панели остаётся как есть: `photo` без pending-платежа показывает меню. Аванс — `Store.GrantAdvance`: флаг и `UpdateUser` под той же блокировкой (только `pending`), так что решение из панели, которому кнопки не нужны, не будет затёрто авансом; сбой панели флаг не откатывает. `payments.username`/`users.username` — настоящий username или пусто (имя в панели без username — telegram id, это делает `pkg/remnawave`). FSM (Redis) — лишь подсказка роутинга фото (`await_photo → in_review → none`). Базой для продления всегда служит `PrevExpireAt`, а не текущий срок в панели (там уже +1 день). Месяц = 30 дней. Время показывать в `Europe/Moscow`.

Правило аванса: неоплаченный аванс = платёж `declined|cancelled` с `advance_granted` после последнего `confirmed`. Таких ≥ `AdvanceLimit` (настройка, дефолт 3; 0 — авансов нет) → аванс не выдаётся; сбрасывается подтверждённой оплатой. Админу в сообщении проверки показывается статистика юзера (`review_stats.go`; у заблокированного вручную — строка «🚫 заблокирован»).

Ручная блокировка (`users.blocked_at`, `POST /api/users/{id}/block|unblock`, идемпотентно) запрещает юзеру все бесплатные выдачи: аванс (`Store.GrantAdvance` → `ErrBlocked`, флаг не ставится, юзер видит обычное «фото на проверке» без строки про доступ) и промокоды любого типа (`checkPromoLocked` → `promo.ErrBlocked`: дни из меню, скидочный платёж `CreatePayment` с промокодом, подтверждение платежа 0 ₽). Бот показывает на `ErrBlocked` текст `promo.not_found` и о блокировке не сообщает. Проверка — внутри той же транзакции, что выдача, простым чтением `blocked_at` без `FOR SHARE` (блокировка строки юзера после платежа встала бы в дедлок с `CreatePayment`: юзер → платёж); ранний отказ в `checkPaymentPromo` — лишь удобство. Обычная оплата (pending, чек, подтверждение админом), напоминания и меню не затрагиваются; уже созданный платёж со скидкой при блокировке остаётся и подтверждается админом. Выдача дней админом из панели блокировкой не запрещена (решение админа). Аудитории рассылок исключают `blocked_at` (с этапа 4).

Выдача дней из панели (`POST /api/users/{id}/grant {days: 1..365}`, `payflow.GrantDays` + `Store.GrantDays`, таблица `grants(id, telegram_id, days, created_at, by_admin_id)`, миграция 00013): в одной транзакции сдвиг `prev_expire_at` pending-платежа (`greatest(prev, now) + N`, как у промокода на дни), `CreateUser`/`UpdateUser` панели абсолютной датой от `max(срок в панели, now)`, строка `grants` и outbox-событие `grant_days` (`TextKey grant.days`, `Days`, `ExpireAt`; текст собирает воркер через `routes.PaymentNotice`). Ошибка панели откатывает транзакцию (502 `panel_unavailable`), сбой коммита после записи в панель — компенсирующий `UpdateUser` на прежний срок (если срок в панели ещё наш). Карточка `GET /api/users/{id}` отдаёт `grants` (последние 20) и `user.blockedAt`; `GET /api/users?tab=blocked` — заблокированные вручную.

Реализация — `bot/internal/handler/routes/`: `tariffs.go` (pay/price/buy), `promo.go` (промокоды), `photo.go`, `review.go` (adm_ok/adm_no), `review_stats.go`.

Промокоды (`core/promo`, `promo.go`): тип `percent` (1..100) / `rub` (1..1 000 000) — скидка при оплате, `days` (1..3650) — бонусные дни из кнопки «Промокод» главного меню. Код — `A-Z0-9_-`, 3–32 символа, хранится через `promo.Normalize` (trim + upper); `Generate` — 8 символов из алфавита без I/O/0/1. Ограничения: `max_activations`, `starts_at` (необязательно, миграция 00012), `expires_at`, `only_new` (нет ни одного `confirmed`), персональный `telegram_id`, `disabled`. `promo.Check` отдаёт первую причину в порядке: disabled → not started (`now < starts_at`, `ErrNotStarted`, текст `promo.not_started`) → expired (`now >= expires_at`) → exhausted → not yours → only new → already used (`UNIQUE(promo_id, telegram_id)`) → wrong place (скидка в меню / дни при оплате). `promo.Apply`: percent `base*(100-v)/100`, rub `base-v`, не ниже 0; days цену не меняет. Скидка: на «Верно?» кнопка «Есть промокод» → FSM `await_promo` (data `{month}`) → код сообщением → тариф со скидкой и кнопкой «Убрать промокод»; «Да» (`buyp:<месяцы>:<id>`) заново проверяет код и тариф, под CAS-замком `promo_paying` (от двойного «Да»), создаёт платёж с `promo_id`, `base_price` и ценой со скидкой, дальше обычный флоу. Цена 0 → фото не ждём (FSM `none`): платёж сразу `confirmed` через `ResolvePayment` (`PrevExpireAt + Month*30d`, `UpdateUser` и `payment_result` в одной транзакции), админу — «Оплата промокодом»; сбой подтверждения → `CancelPayment`. Дни: FSM `await_promo_days` → `Store.ActivateDaysPromo` (под блокировкой кода: `Check`, сдвиг `prev_expire_at` pending-платежа юзера на те же дни (`greatest(prev, now) + N`, иначе confirm/decline затрёт бонус), продление от `max(срок в панели, now)` через `CreateUser`/`UpdateUser`, запись активации; ошибка панели откатывает активацию, сбой коммита после продления — компенсирующий `UpdateUser` на прежний срок). Ошибки показываются по тексту `promo.*` (стейт ожидания остаётся — можно прислать другой код); команда/фото/нетекст выходят из ожидания (`leavePromo` восстанавливает стейт по pending-платежу). Активация скидочного кода записывается в `ResolvePayment` при `confirmed` (для цены > 0 — без проверки лимита, `ON CONFLICT DO NOTHING`; для 0 — под блокировкой строки кода заново `promo.Check`: последняя активация достаётся одному, отказ (`promo.Err*`) откатывает транзакцию, юзер видит причину), а не при показе скидки; отклонённый/отменённый платёж код не расходует. Админу в сообщении проверки — строка о промокоде (`promoLine`) и «к оплате N ₽ (было M ₽)». Застрявший после падения `promo_paying` снимает `leavePromo` (/start, меню, любое сообщение).

Outbox: все уведомления, не являющиеся ответом на действие юзера (результат проверки, напоминания, рассылка), кладутся в таблицу `outbox(id, event_type, payload)` (payload — jsonb; `payment_result`, `reminder`, `broadcast`, `broadcast_summary`, `direct`, `text_test`, `payment_admin_closed`) и доставляются воркером `internal/outbox`; обработанная строка удаляется. Фото — `Photo` (Telegram `file_id`): есть → `sendPhoto` с подписью `Text`. Флаг `Template` (есть `{{.x}}` в рассылке, личном сообщении, «Отправить мне»): воркер подставляет общие переменные на получателя при доставке через `content.Provider.Render` (настройки из снимка, не больше одной строки `users` на доставку, значения экранированы); без флага текст уходит как есть — старые строки и обычный текст с «{{». Рассылки и личные сообщения: счётчики и итог живут в БД (`broadcasts(id uuid, idempotency_key UNIQUE, text, photo, total/sent/failed, finished_at)`, `direct_messages(status pending|sent|failed)`; миграция 00005), воркер пишет доставку (`BroadcastDelivered`/`FinishBroadcast`/`DirectDelivered`) и собирает `broadcast_summary` из БД; старые строки без `Broadcast`/`DirectID` доставляются как раньше (строки старой `/a`: `Broadcast` — uuid, которого нет в `broadcasts`, поэтому счётчики не пишутся, а итог — «Рассылка завершена» без цифр); `bot_broadcasts_total` растёт по итогу. `payment_result` пишется в транзакции `ResolvePayment`. Напоминания в `ReminderTimes` (настройка, список `HH:MM` Europe/Moscow: 1..6 без повторов, по возрастанию; старый ключ `reminderTime` читается как список из одного; бот переставляет cron-задачи (по одной на время) без перезапуска, `NOTIFICATION_CRON` — только дефолт: все часы выражения `M h1,h2 * * *` при одной минуте; другое выражение или больше 6 часов → `12:00` + warn): «скоро закончится» (≤`ReminderWeekDays`, дефолт 7 дн.) и «заканчивается» (≤`ReminderDayHours`, дефолт 24 ч), по одному разу на дату окончания; дедуп-ключ `notify:<id>:<expireAt unix>:<week|day>` остаётся в Redis, TTL = первый порог + сутки. Код — `internal/reminder` (отбор/дедуп, кладёт в outbox), текст — `routes.ReminderMessage`.

Рассылки — жизненный цикл (миграция 00011, `core/broadcast`, `Store.SendBroadcast`/`ClaimDue`): `broadcasts.status` = `draft|scheduled|sending|sent|cancelled`. Отправка (`POST /api/broadcasts`) создаёт строку `scheduled` (с `DraftID` — переводит черновик, получающий `idempotency_key`) и, если `scheduled_at` пуст, в той же транзакции запускает её; повтор с тем же ключом возвращает ту же рассылку (200, outbox не трогается, двойной клик на «Отправить позже» — одна строка). Запуск = `startLocked`: аудитория считается из `users` на момент старта (не заблокировавшие бота и не заблокированные админом), `scheduled → sending` (`WHERE status='scheduled'`), `total`, строки outbox получателям и итог админу — одной транзакцией. Планировщик (`bot/internal/broadcast`, компонент `broadcasts`, тик 20 с, на старте догоняет пропущенное): `Store.ClaimDue` берёт по одной `scheduled` с `scheduled_at <= now` через `FOR UPDATE SKIP LOCKED` и запускает в её же транзакции — рестарт или второй воркер не стартуют рассылку дважды. Правка (`PUT /api/broadcasts/{id}`) и отмена (`POST …/cancel`) — только `draft`/`scheduled`: `UPDATE … WHERE status=…` ждёт блокировку строки у `ClaimDue` и перепроверяет статус, поэтому проигравший получает `ErrBroadcastLocked` → 409 `locked` (правка, державшая блокировку, пропускается `SKIP LOCKED` и стартует на следующем тике со своим содержимым). `FinishBroadcast` переводит `sending → sent`. Время из панели — `scheduledAt` строкой `ГГГГ-ММ-ДДTЧЧ:ММ` по Москве (без пояса и секунд, парсинг `ParseInLocation`, DST нет), в БД UTC; не позже «сейчас» — 400. `GET /api/broadcasts?status=a,b&page=` (статусы через запятую; только `scheduled` — по времени старта), `GET /api/broadcasts/{id}`.

Аудитории рассылки (`audience` + `audienceDays`, `core/broadcast`): `all` — каждый юзер из `users`, кроме `blocked_bot_at` (заблокировал бота) и `blocked_at` (заблокирован админом); `active` — `expire_at > now`; `no_subscription` — `expire_at` пуст или `<= now`; `expiring` — `expire_at` в пределах `(now, now + N дней]`, N 1..60 (обязателен только для `expiring`, у остальных — null, иначе 400). Аудитория считается при старте в `startLocked` из той же функции `audienceWhere`, что и счётчики: `GET /api/broadcasts/recipients?days=N` — все аудитории сразу (`expiring` — если N корректно), `?audience=X[&days=N]` — `{count}` одной (диалог подтверждения перезапрашивает её на момент клика). Юзеры, ни разу не нажавшие /start, но попавшие в `users` из панели, получат рассылку; 403 пометит их `blocked_bot_at` позже. «Пробный период» — этап 8.

Кнопки и «Без звука» (только рассылки; личные сообщения без них): `buttons` — до 3 кнопок, по одной в строке, `{text, url, style}` (`broadcast.ValidateButtons`): текст 1..64 UTF-16 простым текстом без пробелов по краям и без `{{`, ссылка только `https://` с хостом (≤512, без пробелов/управляющих, без userinfo и opaque: `javascript:`, `data:`, `http:`, `tg:` отклоняются), стиль из `texts.Styles`. Хранятся в `broadcasts.buttons` (jsonb); при старте `broadcast.Keyboard` кладёт inline-клавиатуру (url-кнопки) в payload outbox вместе с `silent` → воркер шлёт `ReplyMarkup` и `DisableNotification` и в `sendMessage`, и в `sendPhoto`. «Отправить себе» (`preview-send`) принимает те же `buttons`/`silent`. Превью композера показывает клавиатуру через `MessageBubble keyboard` (кнопки без href).

Черновики и расписание в композере (`web/admin/src/compose/Composer.tsx`): автосохранение через 1,5 с после правки (`PUT /api/broadcasts/{id}` с uuid, выбранным клиентом: создаёт черновик при первой правке и обновляет его, повтор идемпотентен; запросы идут по цепочке; открытие без правок черновик не создаёт; уход со страницы сбрасывает отложенное). Черновик хранится без проверки содержимого (`normalizeDraft`: границы полей, неизвестная аудитория/время — 400, кривые дни `expiring` не сохраняются), все правила применяются при отправке. Отправка черновика — `POST /api/broadcasts` с `draftId`: ждёт идущее сохранение, гасит отложенное, строка получает ключ и статус (`SaveDraft` после этого → 409). Ключ идемпотентности меняется при любой правке содержимого, аудитории, кнопок, «без звука» и времени; двойной клик с тем же ключом — одна строка (200). Запланированная правится явно («Сохранить изменения» → `PUT`, полная проверка, время обязательно, без автосохранения), ключ при этом не трогается: повтор старого POST вернёт ту же (изменённую) строку, дубля нет. Время — `datetime-local` по Москве (`compose/schedule.ts`, подпись «по московскому времени (UTC+3)»). Экраны: `/broadcasts/new`, `/broadcasts/:id/edit` (черновик или запланированная; запущенная и отменённая — редирект). Вкладки списка — фильтр `status` на сервере: Все / Запланированные (`scheduled`) / Отправленные (`sending,sent`) / Черновики (`draft`).

Данные юзера (`users`, миграция 00007): `first_name`, `last_name`, `last_seen_at` — пишет `middleware.LastSeen` после хендлера (сообщение в личке или кнопка; upsert, так что в таблице и те, кто только нажал /start; не чаще раза в 5 минут на юзера в памяти процесса; сбой только в лог) и заодно снимает `blocked_bot_at`. `expire_at`, `panel_status` (`NULL` — нет в панели), `synced_at` — копия панели: `core/panelsync.Run` читает панель целиком (сбой или пустой ответ → `ErrPanel`, ничего не записано), затем одной транзакцией `Store.ApplyPanelSync` заводит новых юзеров, снимает статус с исчезнувших из панели, запоминает итог в `panel_sync`; строки с `synced_at` позже начала прохода свежее снимка и не трогаются. Запуск: cron бота каждые 15 минут (сбой → лог + `bot_panel_sync_failures_total`) и `POST /api/sync`; не пересекаются через `Store.WithPanelSyncLock` (`pg_try_advisory_lock`, занято → `ErrSyncRunning`). Запись сразу после вызова панели: декоратор `routes.writeThrough` в `Register` (`CreateUser`/`UpdateUser` любого хендлера) → `Store.SetUserPanel`, строку под блокировкой пропускает (`SKIP LOCKED`: `CreatePayment` держит её, пока ждёт панель; ожидание было бы дедлоком), пропуск дочинит синхронизация. `blocked_bot_at` ставит outbox-воркер на 403 (первое время сохраняется), `broadcasts_received` растит на доставке `broadcast` (после удаления строки: повтор отправки не удваивает, падение между удалением и записью теряет отметку). `blocked_at` пока не используется (этап 6).

Глобальные переменные: в любом тексте реестра (сообщение, кнопка, простой) доступны общие — системные `{{.name}}`, `{{.username}}`, `{{.telegramId}}`, `{{.expireAt}}` (МСК, нет значения — «—»), `{{.phone}}`, `{{.bank}}`, `{{.supportUrl}}` и свои из `Settings.Vars` (ключ `vars`: имя `^[a-zA-Z][a-zA-Z0-9_]*$`, не занято (`texts.Reserved`), значение до 96 символов (`texts.MaxCustomVar`, UTF-16; проверяется только при `PUT /api/settings` через `ValidateForSave` — `Validate` при загрузке длину не смотрит, чтобы сохранённые длиннее 96 не сбрасывали бота на env-дефолты; `GET /api/settings` отдаёт их в `problems` без `usingDefaults`, панель просит сократить и не даёт сохранить), экранируется как обычная переменная). С переменными текстов (`Def.Vars`) имена не пересекаются — тест реестра. Значения собирает единственное место — `content.Provider`: настройки из одного снимка с телом текста, получатель из контекста: `middleware.TextUser` кладёт автора апдейта (`content.WithUser`), для другого адресата — `content.ForUser(ctx, id)` (админ решает платёж, напоминание, outbox). `users` читается одной строкой (`Store.UserContact`) и только если тело просит то, чего нет в контексте. Значение от вызывающего важнее (`expireAt` — только что посчитанный срок). Неизвестная переменная рендерится пустой, а при загрузке (`ValidateStored`) не отменяет правку; весь текст пуст → текст по умолчанию (Telegram отверг бы). При сохранении `Validate` строг: неизвестная и неразборчивая (`{{name}}`, `{{.a b}}`) → 400; длина по худшему случаю (`Var.Max`, свои — 96, сохранённое длиннее считается по факту). Кнопки и простые тексты (лимит 64 UTF-16, `maxButtonLen`) при рендере не обрезаются: `Validate` считает худший случай (общие и свои переменные текста — `Var.Max`, свои общие — по ТЕКУЩЕМУ значению) и при превышении отдаёт 400 «{{.name}} может не влезть в кнопку: до 64 символов» (называет самую длинную переменную; `{{.name}}` в одиночку — ровно 64 — проходит, `telegramId`/`expireAt` коротки). Последняя страховка в `content.Provider.Text`: пустая подпись или длиннее 64 (`texts.FitsPlain`; например значение переменной поменяли в БД в обход API) → текст по умолчанию + warn один раз на ключ, никогда не пусто и не длиннее лимита; сохранённая правка, переставшая проходить `ValidateStored`, и так отбрасывается до дефолта. Удалить свою переменную из сохранённого текста нельзя, а изменить её значение так, чтобы сохранённая кнопка или простой текст перестали влезать, тоже: `PUT /api/settings` → 400 с ключами текстов.

## Админка

Платежи: `POST /api/payments/{id}/confirm|decline` (200 — платёж; повтор — 409 `already_resolved`; нет — 404 `not_found` «Платёж устарел»; панель — 502 `panel_unavailable`, транзакция откатана; вызов панели с потолком `PanelTimeout`, запрос живёт и после закрытия вкладки). `GET /api/payments/{id}/photo` — чек потоком через Bot API (`file_id` в `payments.photo_file_id`, наружу только `hasPhoto`; тип по содержимому, только jpeg/png/webp, `Cache-Control: private`, до 20 МБ, 30 с; нет чека или `file_id` устарел — 404). На экране и в карточке — кнопки с `Dialog` и чек в `Sheet` (`pages/payment-review.tsx`, `PaymentReceipt.tsx`); на телефоне строка раскрывается в те же кнопки. Экран «Платежи»: вкладки Все/Оплачено/Ожидают/Отклонён/Отменён (серверный `status`), «Фильтры» — только период (по дате создания), выручка — по дате подтверждения; «Дата» — подтверждения у оплаченных, иначе создания; пометка аванса; код и «было M ₽» (`promoCode` — подзапрос в `paymentCols`).

Экраны SPA: Обзор (`/`; карточки одним `GET /api/overview`: `users{total,new7,prev7}`, `promos{active,activations7}`, `pending`, `revenue{week,prevWeek}` — окна по дням МСК (сегодня и 6 предыдущих / 7 до них), упавшая секция = `null`, остальные считаются; «Последние платежи» и «Ближайшие рассылки» — отдельные запросы), Рассылки (`/broadcasts`, `/broadcasts/new`, `/broadcasts/:id`, `/broadcasts/:id/edit`), Промокоды (`/promos`, `/promos/new`), Пользователи, Платежи, Редактор сообщений (`/texts`, tiptap-редактор → Telegram-HTML, санитизированное превью, «тест» шлёт текст админу через outbox `text_test`), Настройки (`PUT /api/settings` атомарно). Карточка юзера: «Выдать дни» (Dialog с числом 1–365, чипы 7/14/30, дата результата считается на клиенте от срока в панели; блок «Выдачи» — `grants`) и «Заблокировать»/«Снять блокировку» (Dialog с последствиями; тег «Заблокирован» в карточке и в «Статус» списка поверх статуса панели; вкладка «Заблокированы мной» = `tab=blocked`). Промокоды (экран `/promos`: вкладки Все/Активные/Истёкшие, «Фильтры» = тип и для кого, строка раскрывается в список активаций, «Выключить»/«Включить» (флаг `disabled`, удаления нет), статус «Ещё не действует» при `validFrom` в будущем; форма создания на `/promos/new` с кнопкой «Сгенерировать»): `GET /api/promos?status=all|active|expired|disabled&kind=percent|rub|days&target=all|new|user` (фильтры на сервере, по И; `expired` — не выключенные с прошедшим сроком), `POST /api/promos` (`code` пустой → генерация, до 5 попыток при коллизии; `kind`, `value`, `maxActivations`, `validFrom` (`ГГГГ-ММ-ДД` МСК, начало дня включительно; `starts_at` < `expires_at`, иначе 400), `validUntil` `ГГГГ-ММ-ДД`, `onlyNew`, `user` — telegram id или `@username` из `users`; 201, занятый код → 409 `exists`, невалидное → 400 `invalid` с причиной из `ValidateNew`), `POST /api/promos/{id}/disable` и `/enable` (204/404; enable только снимает `disabled`, повтор — no-op), `GET /api/promos/{id}/activations`. `validUntil` — включительная дата МСК: в БД `expires_at` = следующая полночь МСК, наружу отдаются и `expiresAt` (сырое), и `validUntil` (= `expires_at` − 1 день); `startsAt` (сырое) и `validFrom` — дата начала в МСК; прошедшая дата — отказ. API: `GET /api/texts` (`items` + `globals`: системные и свои с описанием, примером и `max`), `PUT|DELETE /api/texts/{key}`, `POST /api/texts/{key}/test`, `GET|PUT /api/settings`. Тексты юзеру и настройки (тарифы, реквизиты, комментарии, ссылка поддержки, карточка «Бот»: времена и пороги напоминаний, лимит и длина аванса) живут в БД (`texts`, `settings`), значение из env (`PAYMENT_*`, `SUPPORT_URL`, `NOTIFICATION_CRON`) — лишь дефолт, пока настройки не сохранены. У настроек сброса нет: после первого сохранения все ключи живут в БД и правки env больше не применяются. Если сохранённые настройки не проходят `Validate`, бот работает на env-дефолтах, а `GET /api/settings` отдаёт `usingDefaults` + `problems`. Сброс (DELETE) есть только у текстов. Тексты, адресованные админу, остаются в коде. Редактор показывает чипы двумя группами: «Общие» и «Этого сообщения» (описание и пример — `Tooltip` DS при наведении и фокусе, не `title`), строку «когда отправляется» (`Def.When`, обязательно в реестре) и карточку «Кнопки»: кнопки сообщения (`Def.Buttons`) с подписью, 4 стилями и действием в коде (`Def.Route`); сохраняется по одной через `PUT /api/texts/{key}` `{body, style}`. Свои переменные — карточка «Переменные» в настройках.

Пользователи: `GET /api/users?q=&page=&tab=active|trial|blocked_bot&hasPayments=&hasUnpaidAdvances=&from=&to=` → `{items,total,page,pages}` (по 50; `q` — подстрока username и имени или telegram id; `active` — `panel_status = ACTIVE` и срок в будущем; `trial` пуст до этапа 8; `from`/`to` — включительные даты регистрации МСК; неоплаченный аванс — то же условие `unpaidAdvance`, что в `UserStats`). Строка: `name`, `expireAt`, `panelStatus`, `blockedBotAt`, `tariffMonths` (последний подтверждённый платёж), `lastSeenAt`, `broadcastsReceived`. Карточка `GET /api/users/{id}` добавляет `promos` (применённые коды) и `panel.id` — числовой id в панели (UUID юзера `remnawave-api-go` не отдаёт, `vlessUuid` — ключ доступа, наружу не отдавать). Синхронизация: кнопка в шапке → `POST /api/sync` (синхронно, потолок 50 с): 200 `{total,updated,finishedAt}`, 409 `sync_running`, 502 при сбое панели (данные не тронуты); `GET /api/sync` → `{lastSyncAt}`. После успеха `useSyncKey` (outlet context) перезагружает Обзор, Пользователей и карточку.

Рассылки (экран «Рассылки») и личные сообщения («Написать» в карточке юзера; карточка отдаёт `messages`): редактор + фото + превью с клавиатурой, получатели (радио с числами), кнопки, «Отправить позже» (МСК), «Без звука», «Отправить мне» (`POST /api/broadcasts/preview-send`, тоже с кнопками и `silent`), подтверждение диалогом (получатели, время, звук; число перезапрашивается при клике). История на `/broadcasts`: вкладки Все / Запланированные / Отправленные (`sending,sent`) / Черновики — фильтр `status` на сервере; «Фильтры» = период по `created_at` (`from`/`to` `ГГГГ-ММ-ДД` по МСК, `to` включительно, оба необязательны, `to` раньше `from` — 400); колонки «Кнопки» (число) и «Аудитория», без «Открыли» (Bot API не сообщает прочтений). Клик по строке: черновик → `/broadcasts/:id/edit`, остальные → `/broadcasts/:id`. Экран рассылки (`GET /api/broadcasts/{id}`): сообщение (то же санитизированное превью, клавиатура, фото-заглушка), аудитория, звук, расписание (МСК), счётчики sent/failed/total и прогресс (опрос раз в 5 с, пока `sending`); действия: «Изменить» (черновик/запланированная), «Отменить рассылку» (запланированная; диалог; запущенная — 409 `locked`), «Дублировать» (копирует содержимое, аудиторию, кнопки, звук, но не время). `POST /api/broadcasts` (`idempotencyKey`, `draftId?`, `text`, `photo`, `audience`, `audienceDays`, `silent`, `buttons`, `scheduledAt?`): 201, повтор — 200. Обзор: карточка «Платежи на проверке» (все pending за всё время, ссылка на `/payments?tab=pending`, которая открывает вкладку «Ожидают» за всё время) и «Ближайшие рассылки» (до 3 `scheduled`, клик → экран рассылки). Фото: `POST /api/photos` (multipart, нужна сессия, но не `application/json`; jpeg/png/webp ≤10 МБ) заливает файл админу в чат и возвращает `file_id`. Подпись ≤1024 с фото, ≤4096 без, с переменными — по худшему случаю; неизвестная или неразборчивая переменная — 400 при создании. Чипы и превью с примерами — из `globals` в `GET /api/texts`. Личное: `POST /api/users/{id}/messages` (без кнопок и «без звука»). Всё уходит через outbox.

Идентичность: `GET /api/me` → `{telegramId, username, name, bot:{username,name}}`; админ — из `users` (иначе `getChat` через `api/internal/telegram`), бот — `getMe`; удачный ответ кэшируется в памяти api, неудачный повторяется не чаще раза в 30 с, поля пустые, не 500. Публичный `GET /auth/bot` (без сессии, для страницы входа) отдаёт только `{username,name}` бота. Фронт: `useMe()` (`web/admin/src/me.ts`, контекст в `AppShell`), констант имён в коде нет; пусто — элемент скрыт. Поиск в шапке — «Поиск пользователей» (`/users?q=`).

Контраст (F4): активный пункт меню (сайдбар) и текста — `bg-accent-strong text-on-accent-strong`, активная вкладка телефона — `text-accent-strong`; пары ≥ 4.5:1 в обеих темах проверяет `web/admin/src/styles/contrast.test.ts` по `design/tokens.json`.

Вход: `/login` в боте (или deep link `?start=login` со страницы входа: `/start login` от админа вызывает тот же `login`, от остальных — обычное приветствие, без токена и намёка) → inline-кнопка со ссылкой `ADMIN_BASE_URL/auth?token=…` (токен одноразовый, 5 мин; ссылка только в кнопке, превью отключено) → сессионная cookie `bn_session` на 24 ч. `/api/*` — default-deny: без сессии 401, мутирующие принимают только `application/json`. Админ один — `TELEGRAM_ADMIN_ID`.

Деплой: один образ (bot + api + фронт), compose-сервис `api` (`/app/api`) слушает `127.0.0.1:8090`; наружу — nginx `admin.bruhanet.ru` → `127.0.0.1:8090` (см. README). Prometheus скрейпит `api:8091`. Токен в `/auth?token=…` попадает в access-лог nginx — безвредно (одноразовый), при желании `access_log off` для `location = /auth`.

**SQL только в `core/store`** — api и bot ходят в БД через него.

## Деплой этапа 1 (Postgres)

Деплой этой ветки идёт без живых проверок: до мержа на VPS добавить `POSTGRES_PASSWORD` в `.env` (или прогнать `install.sh` — допишет недостающие ключи); CI-шаг `Check .env keys` упадёт, если ключа нет. Платежи, оставшиеся «на проверке» в Redis FSM, в Postgres не переезжают — бот при старте пишет warn `legacy fsm payment found` с `telegram_id`, разобрать вручную до мержа.

`task` — список. Основное: `task setup`, `task up` (Redis в docker), `task dev SVC=bot` (air + jq), `task run SVC=bot`, `task test`, `task test:db` (SQL-тесты `store` на dev-Postgres, нужен `task up`), `task migrate` (`bot migrate`; `task run`/`task dev` делают это первым шагом), `task lint`, `task fmt`, `task tidy`. Фронт: `task web:install|dev|build|test|lint` (dev-сервер проксирует `/api` и `/auth` на :8090); api локально — `go -C api run ./cmd` (нужен `NOTIFICATION_CRON` — задай в окружении или подгрузи `.env`; он лишь дефолт времён напоминаний: формат `M h1,h2 * * *`, не больше 6 часов, иначе 12:00 + warn).
Образ (bot + api + фронт, без ENTRYPOINT — команда задаётся в compose): `task docker:build` (TAG=local). Прод-стек: `task deploy:config|up|down|pull|ps`, `task deploy:logs -- <service>` (нужен `deploy/.env`, `BOT_IMAGE_TAG=local task deploy:up` для локального образа). Docker healthcheck бота — `/app/bot healthcheck`, api — `/app/api healthcheck` (liveness `/healthz`, readiness не влияет).
Установка/обновление на VPS: `curl -fsSL https://raw.githubusercontent.com/bruhabruh/bruhanet-bot/main/install.sh | bash` (`install.sh` в корне: качает `deploy/`, спрашивает `.env` по `.env.example`, `pull` + `up -d`; существующий `.env` не трогает; env: `BRUHANET_DIR|REF|TARBALL|INPUT|SKIP_UP`).
CI/CD — `.github/workflows/ci.yaml`: lint + test (pkg, core, bot, api) + web (typecheck, lint, test) + build образа на PR и push в `main`; на push в `main` — push в ghcr (`latest`, `sha-<short>`) и деплой по ssh (секреты environment `production`: `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS`, `SSH_HOST`, `SSH_USER`, `WORK_DIR` — абсолютный путь): копирует `deploy/` без `.env`, `pull` + `up -d` с `BOT_IMAGE_TAG=sha-<short>`, ждёт `State.Health.Status == healthy` у bot и api до 90 с, иначе логи migrate/bot/api и fail, `docker image prune -f` (не `-a` — на VPS ещё Remnawave). Порядок деплоя: проверка ключей `.env` (по `deploy/.env.example` раннера) → копирование `deploy/`, так что провал проверки не трогает VPS. Откат — только перезапуском старого деплоя в CI (он вернёт старый `deploy/`), не через `BOT_IMAGE_TAG=… up`: старый образ с ENTRYPOINT сломает команды api/migrate. Grafana по умолчанию на `127.0.0.1:3030` (3000 занят панелью Remnawave).
После CI-деплоя изменения в bind-mount конфигах `prometheus/`, `tempo/`, `loki/`, `alloy/` подхватываются только через `docker compose restart <service>`.
Новый модуль добавлять в `SERVICES` в `Taskfile.yaml` и в matrix в `ci.yaml`.
Redis-реализация FSM тестируется на miniredis, SQL-тесты `store` пропускаются без `TEST_DATABASE_URL` — docker для `task test` не нужен. Хендлеры тестируются через `tgtest` (`bot.WithSkipGetMe` + `WithServerURL` + `WithNotAsyncHandlers`, апдейты через `ProcessUpdate`).

## Конвенции и подводные камни

- Go **1.27**: есть generic-методы, stdlib `uuid`, `errors.AsType`. Не «чинить» их как ошибки. Но generic-метод не реализует метод интерфейса — поэтому `pkg/remnawave` с `int64`.
- UUID — везде `github.com/google/uuid`, не stdlib: его требуют типы `remnawave-api-go`.
- Ошибки: sentinel в `errors.go` пакета, оборачивать через `errors.Join(ErrX, err)`; проверять `errors.Is`.
- Конфиг: только env-теги `caarlos0/env` + `validate`. Новый env — сразу и в `.env.example`.
- Логи: `slog`, контекстный логгер через `stlog.With/L(ctx)`; поля snake_case.
- Линтер строгий (`.golangci.yml`: gosec, errorlint, exhaustive, gocritic…), формат gofumpt + goimports с local-prefix `github.com/bruhabruh/bruhanet`.
- Тексты юзеру на русском, parse mode HTML (`models.ParseModeHTML`). Новый текст юзеру — только через реестр `core/texts` (`Default` = точный текст), рендер только `texts.RenderDef` (экранирует не-Raw переменные); читать через `Content` (`bot/internal/content`); текст другому юзеру, не автору апдейта, — с `content.ForUser(ctx, id)`. Тексты админу — в коде, динамическое через `html.EscapeString`. Плюрализация «месяц/месяца/месяцев».
- Имена файлов — нижний регистр через `_` (`in_memory.go`).
- `MatchFunc` go-telegram выполняется синхронно до всех middleware: только проверки полей, без I/O и паник.
- Роуты регистрируются только в `handler/routes/routes.go` (`Register`), хендлер роута — в своём файле `handler/routes/<route>.go`. Статичная кнопка — `keyboard.Callback(text, "pay")`; с аргументом — `var Price = callback.New[int]("price")`, кнопка `keyboard.Callback(text, Price.Data(6))`, в хендлере `Price.Parse(u.CallbackQuery.Data)`. Callback data подделывается клиентом — аргумент валидировать (тариф есть в `Content.Settings(ctx).Prices`), админские роуты — с `middleware.AdminOnly`.
- Внешние вызовы — только через инструментированные клиенты (Remnawave-декоратор `InstrumentRemnawave`, `TelegramTransport`, Redis-хук); пробы зависимостей — через `observability.WithProbe` или необорачиваемый клиент. telegram_id/request_id/error в метки метрик не класть.
- SQL — только в `core/store`. Миграции — отдельный one-shot `bot migrate` (в проде сервис `migrate`, бот стартует после него); `app.New` лишь делает `CheckSchema` (есть непримененные → `ErrSchemaOutdated`, бот не стартует). Уведомление, не являющееся ответом на действие (результат проверки, напоминание, рассылка), — только через outbox.
- Стили кнопок — только `keyboard.Style*` константы. Кнопка с подписью из реестра строится через `callbackButton|urlButton|copyButton` (`routes/buttons.go`): стиль из аргумента — вид на этом экране, пока админ не сохранил свой в `texts.style` (nullable, миграция 00008; `body` там же nullable: изменён только стиль). Сохранён вид по умолчанию (`Def.Style`) — снова `NULL`, на других экранах у кнопки опять их вид из кода. `DELETE /api/texts/{key}` сбрасывает и подпись, и стиль. Новая кнопка на экране — и в `Def.Buttons` этого сообщения (тест `TestDeclaredButtons`).
- На callback отвечать через `middleware.Answer`, или повесить на роут `middleware.AutoAnswer("текст")` (toast после хендлера); иначе глобальный `AutoAnswer()` ответит пустым.
- Служебное состояние апдейта (route, answered, panicked) — `middleware.UpdateInfoFrom(ctx)`; это не логирование.
- Дизайн каркаса хендлеров: `docs/superpowers/specs/2026-10-26-bot-handler-infra-design.md`.
- Callback data в старом боте — короткие коды `"0".."5"` + `:<arg>` (лимит Telegram 64 байта).
- Грабли старого кода, не повторять: обращение к `payment.*` до проверки `err` (nil-паника), повторное нажатие Подтвердить/Отклонить, игнор ошибок `UpdateUser` при выдаче 1 дня, admin-хендлеры без проверки `AdminID`.
- Экраны по callback — `show` (редактирование на месте, fallback — новое сообщение); ответы на фото/текст — `send`.
- Remnawave в хендлерах — только через `routes.Remnawave`; в тестах `tgtest.NewRemnawave`. Время — `h.now()` (поле `handlers.now`).
- Message-роуты роутера матчатся в порядке регистрации в `routes.Register` (= приоритет). Рассылки и личные сообщения — только из веб-админки (api кладёт в outbox); команды `/a` в боте нет — от админа это обычное сообщение (меню).
