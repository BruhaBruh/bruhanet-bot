# BruhaNet bot

Telegram-бот продажи VPN-подписок (панель Remnawave). Оплата — ручной перевод на карту, подтверждает админ.
Переписка старого бота (`tmp/*.go`, пакет `tgbot`, в git не попадает — `.gitignore: tmp/`). Старый код — эталон поведения и текстов, не архитектуры.

## Флоу оплаты

1. `/start` или любое сообщение → приветствие + главная клавиатура (Информация / Оплатить / Подписка (copy URL) / Поддержка; без юзера в панели — только «Купить»).
2. «Оплатить»/«Продлить» → клавиатура тарифов из настроек (`Content.Settings`, дефолт — env `PAYMENT_PRICES`; месяцы → ₽, по 2 в ряд).
3. Выбор тарифа → «Верно?» Да/Нет.
4. «Да» → `CreateUser` в Remnawave (если нет; `expireAt=now`). Если у юзера уже есть `pending`-платёж — он становится `cancelled`, юзеру откатывается срок (`PrevExpireAt`), старое админ-сообщение закрывается. Новый платёж — строка `payments` со статусом `pending` (`telegram_id, username, months, price, prev_expire_at` = текущий срок юзера). Показать реквизиты (телефон, банк, комментарии «На кофе»/… — из настроек, дефолты `PAYMENT_PHONE`/`PAYMENT_BANK`).
5. Юзер шлёт фото при наличии pending → фото копируется админу + сообщение с кнопками Подтвердить/Отклонить (в callback `adm_ok`/`adm_no` — **id платежа**).
6. Аванс: `max(now, PrevExpireAt) + 24h`, платёж помечается `advance_granted`. Юзеру — «фото на проверке, доступ на 1 день» (при исчерпанном лимите — без строки про доступ).
7. Админ: **Подтвердить** → `max(PrevExpireAt, now) + Month*30d`; **Отклонить** → вернуть `PrevExpireAt`. Оба: статус `confirmed`/`declined`, убрать клавиатуру, реакция 👍/👎, уведомить юзера.

Инварианты: платёж живёт в Postgres (`payments`, не более одного `pending` на юзера — частичный unique index; статусы ровно `pending|confirmed|declined|cancelled`). Решение админа — `Store.ResolvePayment` под блокировкой строки: в той же транзакции вызывается `UpdateUser` (ошибка панели откатывает транзакцию, повтор считает ту же дату) и кладётся `payment_result` в outbox; повторное нажатие → «Уже обработано», нет платежа → «Платёж устарел». FSM (Redis) — лишь подсказка роутинга фото (`await_photo → in_review → none`). Базой для продления всегда служит `PrevExpireAt`, а не текущий срок в панели (там уже +1 день). Месяц = 30 дней. Время показывать в `Europe/Moscow`.

Правило аванса: неоплаченный аванс = платёж `declined|cancelled` с `advance_granted` после последнего `confirmed`. Таких ≥ `advanceLimit` (3) → аванс не выдаётся; сбрасывается подтверждённой оплатой. Админу в сообщении проверки показывается статистика юзера (`review_stats.go`).

Реализация — `bot/internal/handler/routes/`: `tariffs.go` (pay/price/buy), `promo.go` (промокоды), `photo.go`, `review.go` (adm_ok/adm_no), `review_stats.go`.

Промокоды (`core/promo`, `promo.go`): тип `percent` (1..100) / `rub` (1..1 000 000) — скидка при оплате, `days` (1..3650) — бонусные дни из кнопки «Промокод» главного меню. Код — `A-Z0-9_-`, 3–32 символа, хранится через `promo.Normalize` (trim + upper); `Generate` — 8 символов из алфавита без I/O/0/1. Ограничения: `max_activations`, `expires_at`, `only_new` (нет ни одного `confirmed`), персональный `telegram_id`, `disabled`. `promo.Check` отдаёт первую причину в порядке: disabled → expired (`now >= expires_at`) → exhausted → not yours → only new → already used (`UNIQUE(promo_id, telegram_id)`) → wrong place (скидка в меню / дни при оплате). `promo.Apply`: percent `base*(100-v)/100`, rub `base-v`, не ниже 0; days цену не меняет. Скидка: на «Верно?» кнопка «Есть промокод» → FSM `await_promo` (data `{month}`) → код сообщением → тариф со скидкой и кнопкой «Убрать промокод»; «Да» (`buyp:<месяцы>:<id>`) заново проверяет код и тариф, под CAS-замком `promo_paying` (от двойного «Да»), создаёт платёж с `promo_id`, `base_price` и ценой со скидкой, дальше обычный флоу. Цена 0 → фото не ждём (FSM `none`): платёж сразу `confirmed` через `ResolvePayment` (`PrevExpireAt + Month*30d`, `UpdateUser` и `payment_result` в одной транзакции), админу — «Оплата промокодом»; сбой подтверждения → `CancelPayment`. Дни: FSM `await_promo_days` → `Store.ActivateDaysPromo` (под блокировкой кода: `Check`, сдвиг `prev_expire_at` pending-платежа юзера на те же дни (`greatest(prev, now) + N`, иначе confirm/decline затрёт бонус), продление от `max(срок в панели, now)` через `CreateUser`/`UpdateUser`, запись активации; ошибка панели откатывает активацию, сбой коммита после продления — компенсирующий `UpdateUser` на прежний срок). Ошибки показываются по тексту `promo.*` (стейт ожидания остаётся — можно прислать другой код); команда/фото/нетекст выходят из ожидания (`leavePromo` восстанавливает стейт по pending-платежу). Активация скидочного кода записывается в `ResolvePayment` при `confirmed` (для цены > 0 — без проверки лимита, `ON CONFLICT DO NOTHING`; для 0 — под блокировкой строки кода заново `promo.Check`: последняя активация достаётся одному, отказ (`promo.Err*`) откатывает транзакцию, юзер видит причину), а не при показе скидки; отклонённый/отменённый платёж код не расходует. Админу в сообщении проверки — строка о промокоде (`promoLine`) и «к оплате N ₽ (было M ₽)». Застрявший после падения `promo_paying` снимает `leavePromo` (/start, меню, любое сообщение).

Outbox: все уведомления, не являющиеся ответом на действие юзера (результат проверки, напоминания, рассылка), кладутся в таблицу `outbox(id, event_type, payload)` (payload — jsonb; `payment_result`, `reminder`, `broadcast`, `broadcast_summary`, `direct`, `text_test`) и доставляются воркером `internal/outbox`; обработанная строка удаляется. Фото — `Photo` (Telegram `file_id`): есть → `sendPhoto` с подписью `Text`. Рассылки и личные сообщения: счётчики и итог живут в БД (`broadcasts(id uuid, idempotency_key UNIQUE, text, photo, total/sent/failed, finished_at)`, `direct_messages(status pending|sent|failed)`; миграция 00005), воркер пишет доставку (`BroadcastDelivered`/`FinishBroadcast`/`DirectDelivered`) и собирает `broadcast_summary` из БД; старые строки без `Broadcast`/`DirectID` доставляются как раньше (строки старой `/a`: `Broadcast` — uuid, которого нет в `broadcasts`, поэтому счётчики не пишутся, а итог — «Рассылка завершена» без цифр); `bot_broadcasts_total` растёт по итогу. `payment_result` пишется в транзакции `ResolvePayment`. Напоминания (cron из `NOTIFICATION_CRON`, Europe/Moscow): «скоро закончится» (≤7д) и «в течение суток» (≤24ч), по одному разу на дату окончания; дедуп-ключ `notify:<id>:<expireAt unix>:<week|day>` остаётся в Redis. Код — `internal/reminder` (отбор/дедуп, кладёт в outbox), текст — `routes.ReminderMessage`.

Данные юзера (`users`, миграция 00007): `first_name`, `last_name`, `last_seen_at` — пишет `middleware.LastSeen` после хендлера (сообщение в личке или кнопка; upsert, так что в таблице и те, кто только нажал /start; не чаще раза в 5 минут на юзера в памяти процесса; сбой только в лог) и заодно снимает `blocked_bot_at`. `expire_at`, `panel_status` (`NULL` — нет в панели), `synced_at` — копия панели: `core/panelsync.Run` читает панель целиком (сбой или пустой ответ → `ErrPanel`, ничего не записано), затем одной транзакцией `Store.ApplyPanelSync` заводит новых юзеров, снимает статус с исчезнувших из панели, запоминает итог в `panel_sync`; строки с `synced_at` позже начала прохода свежее снимка и не трогаются. Запуск: cron бота каждые 15 минут (сбой → лог + `bot_panel_sync_failures_total`) и `POST /api/sync`; не пересекаются через `Store.WithPanelSyncLock` (`pg_try_advisory_lock`, занято → `ErrSyncRunning`). Запись сразу после вызова панели: декоратор `routes.writeThrough` в `Register` (`CreateUser`/`UpdateUser` любого хендлера) → `Store.SetUserPanel`, строку под блокировкой пропускает (`SKIP LOCKED`: `CreatePayment` держит её, пока ждёт панель; ожидание было бы дедлоком), пропуск дочинит синхронизация. `blocked_bot_at` ставит outbox-воркер на 403 (первое время сохраняется), `broadcasts_received` растит на доставке `broadcast` (после удаления строки: повтор отправки не удваивает, падение между удалением и записью теряет отметку). `blocked_at` пока не используется (этап 6).

## Структура

Go workspace (`go.work`), модуль-префикс `github.com/bruhabruh/bruhanet`.

- `pkg/` — общее: `app` (CompositeApp + `Run` с graceful shutdown), `lifecycle` (Start/Stop), `cfg` (env → struct + validator), `stlog` (slog + логгер в context), `remnawave` (обёртка `remnawave-api-go/v3`), `tgupdate` (user/chat/type апдейта), `fsm` (стейт + data юзера, `in_memory`/`redis`, CAS — единственное хранилище), `keyboard` (разметка inline-клавиатур, стили-константы), `callback` (имя роута + целый аргумент в callback data, без хранилища).
- `core/` — общее для bot и api: `store` (Postgres: `pgxpool`, goose-миграции через `embed`, платежи/outbox/пользователи/промокоды (`promos.go`); `Migrate`, `CheckSchema`), `panelsync` (синхронизация users с панелью: `Run`, общий код cron бота и ручного запуска api), `promo` (правила промокодов: `Normalize`, `Generate`, `ValidateNew`, `Check`, `Apply`, sentinel-ошибки отказа), `model` (Payment/Outbox/Broadcast/Promo/UserSummary), `texts` (реестр юзерских текстов: `Def{Key,Group,Title,Kind message|button|plain,Default,Vars}`, `RenderDef`, `Validate` — allow-list Telegram-HTML, `Problem`), `settings` (`Settings`: тарифы/телефон/банк/комментарии/ссылка поддержки; `Defaults` из env, `Merge`, `Validate`, `Problems`), `store` также хранит таблицы `texts`/`settings` (миграция 00004), `promo_codes`/`promo_activations` + `payments.promo_id`/`base_price` (миграция 00006), данные юзера и `panel_sync` (миграция 00007), `config` (Database/Telegram/Remnawave/Logger/Payment/Support; `bot/internal/config.Config` их включает). Не импортирует `bot/internal/*`: трейсер Postgres — `store.WithTracer(observability.PostgresTracer())`, probe-контекст — в вызывающем.
- `bot/` — `cmd/main.go` → `internal/app` (wiring), `internal/config` (по файлу на секцию), `internal/handler` (`New` — сборка бота; `handler/router` — роутер; `handler/routes` — все роуты с их хендлерами и клавиатурами, файл на роут; `handler/middleware` — цепочка middleware), `internal/content` (`Provider`: снапшот текстов/настроек из БД с TTL 10 с, неблокирующее обновление с таймаутом 2 с; невалидный override → дефолт + warn один раз), `internal/outbox` (воркер доставки), `internal/reminder`, `internal/observability` (метрики `bot_*`, `/metrics` `/healthz` `/readyz` на `OBSERVABILITY_ADDR`, readiness, трейсинг OTLP → Tempo, подкоманда `bot healthcheck`), `internal/tgtest` (фейковый Telegram API для тестов).
- `api/` — админ-API (`cmd/main.go`, `internal/config`: `API_ADDR` :8090, `internal/telegram` — Bot API только для загрузки фото (`SendPhoto` → `file_id`), `API_OBSERVABILITY_ADDR` :8091; `/app/api healthcheck`) + вшитый фронт (`internal/web`, `//go:embed dist`; в репе заглушка, настоящий `dist` кладёт Dockerfile). `web/` — pnpm workspace, `web/admin` — SPA на React 18 + Vite + Tailwind v4 + примитивы shadcn (`src/ui/primitives`) и компоненты DS в `src/ui`; токены генерируются из `design/tokens.json` командой `pnpm -C web/admin tokens` в `src/styles/tokens.css` (литералы цветов и размеров — только там); `pnpm -C web build` → `web/admin/dist`. Элемент макета без бэкенда: действие — `notWired()` (тост), поле — `disabled` с подсказкой `NOT_WIRED` (`src/lib/not-wired.ts`), и строка в `docs/superpowers/plans/2026-11-06-admin-ds-gaps.md` (gitignored).
- `deploy/` — прод-стек (`docker-compose.yaml`: bot, api, redis, loki, alloy, prometheus, tempo, grafana; конфиги `loki/`, `alloy/`, `prometheus/` (скрейп `bot:8081` и `api:8091`, retention 30d), `tempo/` (OTLP HTTP 4318, retention 720h), `grafana/` (datasources loki/prometheus/tempo, лог → трейс по `trace_id`); `postgres` (том `postgres-data`) и one-shot `migrate`; `.env` не в git, шаблон `.env.example`; `backup` (`deploy/backup/backup.sh`, postgres:18-alpine + curl) — 04:00 МСК `pg_dump -Fc` → Telegram админу + строка в `backups`, сбой → «⚠️ Бэкап не сделан»; бот отдаёт gauge `bot_backup_last_success_timestamp_seconds`, алерты `backup-stale` (>26ч) и `outbox-stuck` (`bot_outbox_pending` > 0 15 мин)).

## Админка

Экраны SPA: Обзор (`/`), Рассылки (`/broadcasts`, `/broadcasts/new`), Промокоды (`/promos`, `/promos/new`), Пользователи, Платежи, Редактор сообщений (`/texts`, tiptap-редактор → Telegram-HTML, санитизированное превью, «тест» шлёт текст админу через outbox `text_test`), Настройки (`PUT /api/settings` атомарно). Промокоды (экран `/promos`: фильтры Все/Активные/Черновики/Истёкшие, строка раскрывается в список активаций, «Выключить» (флаг `disabled`, удаления нет); форма создания на `/promos/new` с кнопкой «Сгенерировать»): `GET /api/promos?status=active|all`, `POST /api/promos` (`code` пустой → генерация, до 5 попыток при коллизии; `kind`, `value`, `maxActivations`, `validUntil` `ГГГГ-ММ-ДД`, `onlyNew`, `user` — telegram id или `@username` из `users`; 201, занятый код → 409 `exists`, невалидное → 400 `invalid` с причиной из `ValidateNew`), `POST /api/promos/{id}/disable` (204), `GET /api/promos/{id}/activations`. `validUntil` — включительная дата МСК: в БД `expires_at` = следующая полночь МСК, наружу отдаются и `expiresAt` (сырое), и `validUntil` (= `expires_at` − 1 день); прошедшая дата — отказ. API: `GET /api/texts`, `PUT|DELETE /api/texts/{key}`, `POST /api/texts/{key}/test`, `GET|PUT /api/settings`. Тексты юзеру и настройки (тарифы, реквизиты, комментарии, ссылка поддержки) живут в БД (`texts`, `settings`), значение из env (`PAYMENT_*`, `SUPPORT_URL`) — лишь дефолт, пока настройки не сохранены. У настроек сброса нет: после первого сохранения все ключи живут в БД и правки env больше не применяются. Если сохранённые настройки не проходят `Validate`, бот работает на env-дефолтах, а `GET /api/settings` отдаёт `usingDefaults` + `problems`. Сброс (DELETE) есть только у текстов. Тексты, адресованные админу, остаются в коде.

Пользователи: `GET /api/users?q=&page=&tab=active|trial|blocked_bot&hasPayments=&hasUnpaidAdvances=&from=&to=` → `{items,total,page,pages}` (по 50; `q` — подстрока username и имени или telegram id; `active` — `panel_status = ACTIVE` и срок в будущем; `trial` пуст до этапа 8; `from`/`to` — включительные даты регистрации МСК; неоплаченный аванс — то же условие `unpaidAdvance`, что в `UserStats`). Строка: `name`, `expireAt`, `panelStatus`, `blockedBotAt`, `tariffMonths` (последний подтверждённый платёж), `lastSeenAt`, `broadcastsReceived`. Карточка `GET /api/users/{id}` добавляет `promos` (применённые коды) и `panel.id` — числовой id в панели (UUID юзера `remnawave-api-go` не отдаёт, `vlessUuid` — ключ доступа, наружу не отдавать). Синхронизация: кнопка в шапке → `POST /api/sync` (синхронно, потолок 50 с): 200 `{total,updated,finishedAt}`, 409 `sync_running`, 502 при сбое панели (данные не тронуты); `GET /api/sync` → `{lastSyncAt}`. После успеха `useSyncKey` (outlet context) перезагружает Обзор, Пользователей и карточку.

Рассылки (экран «Рассылки») и личные сообщения («Написать» в карточке юзера; карточка отдаёт `messages`): редактор + фото + превью, «Отправить мне» (`POST /api/broadcasts/preview-send`), подтверждение диалогом с числом получателей, перезапрошенным при клике; форма на `/broadcasts/new`, история со счётчиками на `/broadcasts` (`GET /api/broadcasts?page=`, `GET /api/broadcasts/recipients`, `POST /api/broadcasts` с `idempotencyKey`: 201, повтор — 200). Фото: `POST /api/photos` (multipart, нужна сессия, но не `application/json`; jpeg/png/webp ≤10 МБ) заливает файл админу в чат и возвращает `file_id`. Подпись ≤1024 с фото, ≤4096 без. Ключ идемпотентности на фронте меняется при любой правке содержимого. Личное: `POST /api/users/{id}/messages`. Всё уходит через outbox.

Вход: `/login` в боте → inline-кнопка со ссылкой `ADMIN_BASE_URL/auth?token=…` (токен одноразовый, 5 мин; ссылка только в кнопке, превью отключено) → сессионная cookie `bn_session` на 24 ч. `/api/*` — default-deny: без сессии 401, мутирующие принимают только `application/json`. Админ один — `TELEGRAM_ADMIN_ID`.

Деплой: один образ (bot + api + фронт), compose-сервис `api` (`/app/api`) слушает `127.0.0.1:8090`; наружу — nginx `admin.bruhanet.ru` → `127.0.0.1:8090` (см. README). Prometheus скрейпит `api:8091`. Токен в `/auth?token=…` попадает в access-лог nginx — безвредно (одноразовый), при желании `access_log off` для `location = /auth`.

**SQL только в `core/store`** — api и bot ходят в БД через него.

## Деплой этапа 1 (Postgres)

Деплой этой ветки идёт без живых проверок: до мержа на VPS добавить `POSTGRES_PASSWORD` в `.env` (или прогнать `install.sh` — допишет недостающие ключи); CI-шаг `Check .env keys` упадёт, если ключа нет. Платежи, оставшиеся «на проверке» в Redis FSM, в Postgres не переезжают — бот при старте пишет warn `legacy fsm payment found` с `telegram_id`, разобрать вручную до мержа.

Прод-стек: `task deploy:config|up|down|pull|ps`, `task deploy:logs -- <service>` (нужен `deploy/.env`, `BOT_IMAGE_TAG=local task deploy:up` для локального образа). Docker healthcheck бота — `/app/bot healthcheck`, api — `/app/api healthcheck` (liveness `/healthz`, readiness не влияет).
Установка/обновление на VPS: `curl -fsSL https://raw.githubusercontent.com/bruhabruh/bruhanet-bot/main/install.sh | bash` (`install.sh` в корне: качает `deploy/`, спрашивает `.env` по `.env.example`, `pull` + `up -d`; существующий `.env` не трогает; env: `BRUHANET_DIR|REF|TARBALL|INPUT|SKIP_UP`).
CI/CD — `.github/workflows/ci.yaml`: lint + test (pkg, core, bot, api) + web (typecheck, lint, test) + build образа на PR и push в `main`; на push в `main` — push в ghcr (`latest`, `sha-<short>`) и деплой по ssh (секреты environment `production`: `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS`, `SSH_HOST`, `SSH_USER`, `WORK_DIR` — абсолютный путь): копирует `deploy/` без `.env`, `pull` + `up -d` с `BOT_IMAGE_TAG=sha-<short>`, ждёт `State.Health.Status == healthy` у bot и api до 90 с, иначе логи migrate/bot/api и fail, `docker image prune -f` (не `-a` — на VPS ещё Remnawave). Порядок деплоя: проверка ключей `.env` (по `deploy/.env.example` раннера) → копирование `deploy/`, так что провал проверки не трогает VPS. Откат — только перезапуском старого деплоя в CI (он вернёт старый `deploy/`), не через `BOT_IMAGE_TAG=… up`: старый образ с ENTRYPOINT сломает команды api/migrate. Grafana по умолчанию на `127.0.0.1:3030` (3000 занят панелью Remnawave).
После CI-деплоя изменения в bind-mount конфигах `prometheus/`, `tempo/`, `loki/`, `alloy/` подхватываются только через `docker compose restart <service>`.
Новый модуль добавлять в `SERVICES` в `Taskfile.yaml` и в matrix в `ci.yaml`.
Redis-реализация FSM тестируется на miniredis, SQL-тесты `store` пропускаются без `TEST_DATABASE_URL` — docker для `task test` не нужен. Хендлеры тестируются через `tgtest` (`bot.WithSkipGetMe` + `WithServerURL` + `WithNotAsyncHandlers`, апдейты через `ProcessUpdate`).

## Конвенции и подводные камни

- Go **1.27**: есть generic-методы, stdlib `uuid`, `errors.AsType`. Не «чинить» их как ошибки. Но generic-метод не реализует метод интерфейса — поэтому `pkg/remnawave` с `int64`.
- UUID — везде `github.com/google/uuid`, не stdlib: его требуют типы `remnawave-api-go`.
- Ошибки: sentinel в `errors.go` пакета, оборачивать через `errors.Join(ErrX, err)`; проверять `errors.Is`.
- Конфиг: только env-теги `caarlos0/env` + `validate`. Новый env — сразу и в `.env.example`.
- Логи: `slog`, контекстный логгер через `stlog.With/L(ctx)`; поля snake_case.
- Линтер строгий (`.golangci.yml`: gosec, errorlint, exhaustive, gocritic…), формат gofumpt + goimports с local-prefix `github.com/bruhabruh/bruhanet`.
- Тексты юзеру на русском, parse mode HTML (`models.ParseModeHTML`). Новый текст юзеру — только через реестр `core/texts` (`Default` = точный текст), рендер только `texts.RenderDef` (экранирует не-Raw переменные); читать через `Content` (`bot/internal/content`). Тексты админу — в коде, динамическое через `html.EscapeString`. Плюрализация «месяц/месяца/месяцев».
- Имена файлов — нижний регистр через `_` (`in_memory.go`).
- `MatchFunc` go-telegram выполняется синхронно до всех middleware: только проверки полей, без I/O и паник.
- Роуты регистрируются только в `handler/routes/routes.go` (`Register`), хендлер роута — в своём файле `handler/routes/<route>.go`. Статичная кнопка — `keyboard.Callback(text, "pay")`; с аргументом — `var Price = callback.New[int]("price")`, кнопка `keyboard.Callback(text, Price.Data(6))`, в хендлере `Price.Parse(u.CallbackQuery.Data)`. Callback data подделывается клиентом — аргумент валидировать (тариф есть в `Content.Settings(ctx).Prices`), админские роуты — с `middleware.AdminOnly`.
- Внешние вызовы — только через инструментированные клиенты (Remnawave-декоратор `InstrumentRemnawave`, `TelegramTransport`, Redis-хук); пробы зависимостей — через `observability.WithProbe` или необорачиваемый клиент. telegram_id/request_id/error в метки метрик не класть.
- SQL — только в `core/store`. Миграции — отдельный one-shot `bot migrate` (в проде сервис `migrate`, бот стартует после него); `app.New` лишь делает `CheckSchema` (есть непримененные → `ErrSchemaOutdated`, бот не стартует). Уведомление, не являющееся ответом на действие (результат проверки, напоминание, рассылка), — только через outbox.
- Стили кнопок — только `keyboard.Style*` константы.
- На callback отвечать через `middleware.Answer`, или повесить на роут `middleware.AutoAnswer("текст")` (toast после хендлера); иначе глобальный `AutoAnswer()` ответит пустым.
- Служебное состояние апдейта (route, answered, panicked) — `middleware.UpdateInfoFrom(ctx)`; это не логирование.
- Дизайн каркаса хендлеров: `docs/superpowers/specs/2026-10-26-bot-handler-infra-design.md`.
- Callback data в старом боте — короткие коды `"0".."5"` + `:<arg>` (лимит Telegram 64 байта).
- Грабли старого кода, не повторять: обращение к `payment.*` до проверки `err` (nil-паника), повторное нажатие Подтвердить/Отклонить, игнор ошибок `UpdateUser` при выдаче 1 дня, admin-хендлеры без проверки `AdminID`.
- Экраны по callback — `show` (редактирование на месте, fallback — новое сообщение); ответы на фото/текст — `send`.
- Remnawave в хендлерах — только через `routes.Remnawave`; в тестах `tgtest.NewRemnawave`. Время — `h.now()` (поле `handlers.now`).
- Message-роуты роутера матчатся в порядке регистрации в `routes.Register` (= приоритет). Рассылки и личные сообщения — только из веб-админки (api кладёт в outbox); команды `/a` в боте нет — от админа это обычное сообщение (меню).
