# BruhaNet bot

Telegram-бот продажи VPN-подписок (панель Remnawave). Оплата — ручной перевод на карту, подтверждает админ.
Переписка старого бота (`tmp/*.go`, пакет `tgbot`, в git не попадает — `.gitignore: tmp/`). Старый код — эталон поведения и текстов, не архитектуры.

## Флоу оплаты

1. `/start` или любое сообщение → приветствие + главная клавиатура (Информация / Оплатить / Подписка (copy URL) / Поддержка; без юзера в панели — только «Купить»).
2. «Оплатить»/«Продлить» → клавиатура тарифов из настроек (`Content.Settings`, дефолт — env `PAYMENT_PRICES`; месяцы → ₽, по 2 в ряд).
3. Выбор тарифа → «Верно?» Да/Нет.
4. «Да» → `CreateUser` в Remnawave (если нет; `expireAt=now`). Если у юзера уже есть `pending`-платёж — он становится `cancelled`, юзеру откатывается срок (`PrevExpireAt`), старое админ-сообщение закрывается. Новый платёж — строка `payments` со статусом `pending` (`telegram_id, username, months, price, prev_expire_at` = текущий срок юзера). Показать реквизиты (телефон, банк, комментарии «На кофе»/… — из настроек, дефолты `PAYMENT_PHONE`/`PAYMENT_BANK`).
5. Юзер шлёт фото при наличии pending → фото копируется админу + сообщение с кнопками Подтвердить/Отклонить (в callback `adm_ok`/`adm_no` — **id платежа**).
6. Аванс: `max(now, PrevExpireAt) + AdvanceHours` (настройка, дефолт 24 ч), платёж помечается `advance_granted`. Юзеру — «фото на проверке, доступ на 1 день» (при исчерпанном лимите — без строки про доступ).
7. Админ (кнопки в боте или панель): **Подтвердить** → `max(PrevExpireAt, now) + Month*30d`; **Отклонить** → вернуть `PrevExpireAt`. Оба: статус `confirmed`/`declined`, убрать клавиатуру, реакция 👍/👎, уведомить юзера.

Инварианты: платёж живёт в Postgres (`payments`, не более одного `pending` на юзера — частичный unique index; статусы ровно `pending|confirmed|declined|cancelled`). Решение админа — одна функция на бота и панель, `core/payflow.Resolve` поверх `Store.ResolvePayment` под блокировкой строки: в той же транзакции вызывается `UpdateUser` (ошибка панели откатывает транзакцию, повтор считает ту же дату) и кладётся `payment_result` в outbox (`TextKey` + `ExpireAt`; текст и главную клавиатуру рендерит воркер при доставке, `routes.PaymentNotice`, у api их нет); из панели (`AdminID` в `Decision`) там же — `payment_admin_closed`: воркер снимает кнопки и ставит реакцию у `admin_message_id` и считает бизнес-метрики, сбой не отменяет платёж. Обратно: решённый в боте платёж панель видит при перезагрузке. Повторное нажатие → «Уже обработано», нет платежа → «Платёж устарел». FSM при решении из панели остаётся как есть: `photo` без pending-платежа показывает меню. Аванс — `Store.GrantAdvance`: флаг и `UpdateUser` под той же блокировкой (только `pending`), так что решение из панели, которому кнопки не нужны, не будет затёрто авансом; сбой панели флаг не откатывает. `payments.username`/`users.username` — настоящий username или пусто (имя в панели без username — telegram id, это делает `pkg/remnawave`). FSM (Redis) — лишь подсказка роутинга фото (`await_photo → in_review → none`). Базой для продления всегда служит `PrevExpireAt`, а не текущий срок в панели (там уже +1 день). Месяц = 30 дней. Время показывать в `Europe/Moscow`.

Правило аванса: неоплаченный аванс = платёж `declined|cancelled` с `advance_granted` после последнего `confirmed`. Таких ≥ `AdvanceLimit` (настройка, дефолт 3; 0 — авансов нет) → аванс не выдаётся; сбрасывается подтверждённой оплатой. Админу в сообщении проверки показывается статистика юзера (`review_stats.go`; у заблокированного вручную — строка «🚫 заблокирован»).

Ручная блокировка (`users.blocked_at`, `POST /api/users/{id}/block|unblock`, идемпотентно) запрещает юзеру все бесплатные выдачи: аванс (`Store.GrantAdvance` → `ErrBlocked`, флаг не ставится, юзер видит обычное «фото на проверке» без строки про доступ) и промокоды любого типа (`checkPromoLocked` → `promo.ErrBlocked`: дни из меню, скидочный платёж `CreatePayment` с промокодом, подтверждение платежа 0 ₽). Бот показывает на `ErrBlocked` текст `promo.not_found` и о блокировке не сообщает. Проверка — внутри той же транзакции, что выдача, простым чтением `blocked_at` без `FOR SHARE` (блокировка строки юзера после платежа встала бы в дедлок с `CreatePayment`: юзер → платёж); ранний отказ в `checkPaymentPromo` — лишь удобство. Обычная оплата (pending, чек, подтверждение админом), напоминания и меню не затрагиваются; уже созданный платёж со скидкой при блокировке остаётся и подтверждается админом. Выдача дней админом из панели блокировкой не запрещена (решение админа). Аудитории рассылок исключают `blocked_at` (с этапа 4).

Выдача дней из панели (`POST /api/users/{id}/grant {days: 1..365}`, `payflow.GrantDays` + `Store.GrantDays`, таблица `grants(id, telegram_id, days, created_at, by_admin_id)`, миграция 00013): в одной транзакции сдвиг `prev_expire_at` pending-платежа (`greatest(prev, now) + N`, как у промокода на дни), `CreateUser`/`UpdateUser` панели абсолютной датой от `max(срок в панели, now)`, строка `grants` и outbox-событие `grant_days` (`TextKey grant.days`, `Days`, `ExpireAt`; текст собирает воркер через `routes.PaymentNotice`). Ошибка панели откатывает транзакцию (502 `panel_unavailable`), сбой коммита после записи в панель — компенсирующий `UpdateUser` на прежний срок (если срок в панели ещё наш). Карточка `GET /api/users/{id}` отдаёт `grants` (последние 20) и `user.blockedAt`; `GET /api/users?tab=blocked` — заблокированные вручную.

Реализация — `bot/internal/handler/routes/`: `tariffs.go` (pay/price/buy), `promo.go` (промокоды), `photo.go`, `review.go` (adm_ok/adm_no), `review_stats.go`.

Промокоды (`core/promo`, `promo.go`): тип `percent` (1..100) / `rub` (1..1 000 000) — скидка при оплате, `days` (1..3650) — бонусные дни из кнопки «Промокод» главного меню. Код — `A-Z0-9_-`, 3–32 символа, хранится через `promo.Normalize` (trim + upper); `Generate` — 8 символов из алфавита без I/O/0/1. Ограничения: `max_activations`, `starts_at` (необязательно, миграция 00012), `expires_at`, `only_new` (нет ни одного `confirmed`), персональный `telegram_id`, `disabled`. `promo.Check` отдаёт первую причину в порядке: disabled → not started (`now < starts_at`, `ErrNotStarted`, текст `promo.not_started`) → expired (`now >= expires_at`) → exhausted → not yours → only new → already used (`UNIQUE(promo_id, telegram_id)`) → wrong place (скидка в меню / дни при оплате). `promo.Apply`: percent `base*(100-v)/100`, rub `base-v`, не ниже 0; days цену не меняет. Скидка: на «Верно?» кнопка «Есть промокод» → FSM `await_promo` (data `{month}`) → код сообщением → тариф со скидкой и кнопкой «Убрать промокод»; «Да» (`buyp:<месяцы>:<id>`) заново проверяет код и тариф, под CAS-замком `promo_paying` (от двойного «Да»), создаёт платёж с `promo_id`, `base_price` и ценой со скидкой, дальше обычный флоу. Цена 0 → фото не ждём (FSM `none`): платёж сразу `confirmed` через `ResolvePayment` (`PrevExpireAt + Month*30d`, `UpdateUser` и `payment_result` в одной транзакции), админу — «Оплата промокодом»; сбой подтверждения → `CancelPayment`. Дни: FSM `await_promo_days` → `Store.ActivateDaysPromo` (под блокировкой кода: `Check`, сдвиг `prev_expire_at` pending-платежа юзера на те же дни (`greatest(prev, now) + N`, иначе confirm/decline затрёт бонус), продление от `max(срок в панели, now)` через `CreateUser`/`UpdateUser`, запись активации; ошибка панели откатывает активацию, сбой коммита после продления — компенсирующий `UpdateUser` на прежний срок). Ошибки показываются по тексту `promo.*` (стейт ожидания остаётся — можно прислать другой код); команда/фото/нетекст выходят из ожидания (`leavePromo` восстанавливает стейт по pending-платежу). Активация скидочного кода записывается в `ResolvePayment` при `confirmed` (для цены > 0 — без проверки лимита, `ON CONFLICT DO NOTHING`; для 0 — под блокировкой строки кода заново `promo.Check`: последняя активация достаётся одному, отказ (`promo.Err*`) откатывает транзакцию, юзер видит причину), а не при показе скидки; отклонённый/отменённый платёж код не расходует. Админу в сообщении проверки — строка о промокоде (`promoLine`) и «к оплате N ₽ (было M ₽)». Застрявший после падения `promo_paying` снимает `leavePromo` (/start, меню, любое сообщение).

Устройства (этап 7): лимит в панели (`hwidDeviceLimit`) = `settings.DevicesBase` (5) + `users.extra_devices`; цена доп. устройства `settings.DevicePrice` ₽/мес, 0 = продажа выключена (кнопки «Устройства» в боте нет, купленные устройства остаются и входят в цену тарифа). Платёж имеет `kind` (`tariff|devices`) и `extra_devices` (миграция 00014). Докупка — отдельный платёж `devices` (`months=0`): экран «Устройства» (информация + «Докупить», `devbuy`) → меню докупки (`devices.buy`: варианты `settings.DeviceOptions`, по умолчанию 1/2/3/5, шаблон `@devices`, и «Своё число» — `devc`: FSM `await_devices`, число сообщением 1..`settings.DeviceMax` (по умолчанию 10), не число или вне границ — `devices.number_invalid` и повторный ввод; команда/фото выходят из ожидания, как у промокода, через `leavePromo`) → «Верно?» (`dev:<n>`, n проверяется по `DeviceMax`) → реквизиты → чек → подтверждение админом; цена `devices.ProratedPrice` = ceil(DevicePrice × n × дни_до_конца / 30), дни округляются вверх, минимум 1 ₽, подписка закончилась — докупки нет («после продления»). Для devices нет промокодов и аванса; срок не меняется ни при подтверждении, ни при отклонении (`payflow.Resolve` пишет только `SetDeviceLimit`); открытая оплата юзера → докупку не создаём (`store.ErrPendingExists`, текст `devices.busy`), а новая оплата подписки отменяет открытую докупку и читает срок заново. Подписка: цена = тариф + `extra_devices` юзера × DevicePrice × месяцы (`quote`), на «Верно?» разбивка и кнопка «Без доп. устройств» (`buyd:<мес>`: цена только тарифа, подтверждение сбрасывает устройства до базы); число устройств фиксируется в `payments.extra_devices` при создании, подтверждение применяет его, а не пересчитывает. Скидка промокода считается от итога (`base_price` = тариф + устройства). `ResolvePayment` берёт под замком юзера (advisory → users → payment) текущее `users.extra_devices` (`Payment.UserExtra`) и после подтверждения пишет `Payment.ExtraAfter`; панель вызывается `payflow.ApplyDeviceLimit` только если число меняется (докупка — всегда, подписка — при изменении). Лимит в панель пишется ТОЛЬКО при событии с устройствами и при создании юзера ботом (`ensureUser`: база + 0); `UpdateUser`/`CreateUser`/синхронизация лимит не трогают и `users.extra_devices` из панели не зеркалят (ручная правка лимита в панели не отражается в боте — до следующего события с устройствами). Аванс сохраняет лимит (пишет только срок). Подтверждающий платёж сам (`payByPromo`) обязан звать `payflow.ApplyDeviceLimit`. Админка: «Устройства» в Настройках (`devicesBase`, `devicePrice`), строка «Устройства» в карточке юзера (`devices{base,extra,price}`), метка «Подписка»/«Устройства» и «+N устр.» в платежах, свой текст диалога подтверждения. Заблокированный юзер докупать устройства может (платная операция). Экран «Устройства» (`devices.menu`) доступен любому юзеру панели независимо от продажи (кнопка «Устройства» в меню, `route:devices` с Guard `in_panel`); «Докупить» — только при `DevicePrice > 0`. Он показывает «Подключено N из лимита» (число устройств из панели через `Remnawave.UserDevices`, сбой панели — «—»), «🧹 Очистить устройства» (`devclr` → подтверждение `devices.clear_confirm` → `devclry` → `DeleteAllUserDevices`, лимит и срок не меняются, ошибка панели — `error.generic`) и «📲 Управлять устройствами» (`link:miniapp`, адрес `settings.MiniAppURL`, условие `miniapp_on`; пусто — кнопки нет): точечное удаление по одному делает юзер в MiniApp, не бот. Потолок докупки: база + купленные ≤ `devices.MaxTotal` (100), `devices.Room`; в меню докупки и в «Своё число» предлагается не больше места до предела (`devices.limit` при нуле). Условия «подтверждённая оплата» для «только новым» и сброса неоплаченных авансов, а также «тариф» юзера считают только `kind='tariff'`.

Пробный период (`core/store/trial.go`, `payflow.StartTrial`, `routes/trial.go`): настройки `trialDays` (0..30, 0 = выключен, дефолт 0: включается в Настройках) и `trialDevices` (1..100, дефолт 2). Кнопка «Пробный период» в меню — только если включён, срок в панели не действует (`payflow.TrialPanelOK`) и `Store.TrialAllowed`; решает транзакция `Store.StartTrial` под `lockUserTerm`: не заблокирован, `users.trial_used_at IS NULL`, нет ни одного `confirmed`, неоплаченных авансов (с пробным) < `advanceLimit`; в панели — юзера нет либо срок не в будущем и не дальше `createdAt+1ч` (иначе старый платящий клиент вне БД — отказ). Внутри: сдвиг `prev_expire_at` pending на те же дни, `CreateUser` при отсутствии, абсолютный срок `now+days·24ч` и `SetDeviceLimit(trialDevices)`, `trial_used_at`, строка `grants` (`source='trial'`, `by_admin_id` NULL, в карточке «Выдано админом» не показывается), `trial.started` в outbox. Сбой панели откатывает всё; сбой после записи в панель возвращает срок и лимит (база). Отказ нейтральный (`trial.unavailable`). **Пробный = один неоплаченный аванс** до первого `confirmed` тарифа (`trialOpen` в SQL, `userStats`: `UnpaidAdvances` +1, фильтр «Неоплаченные авансы»). Первое подтверждение подписки после пробного пишет лимит `base+extra` один раз (`Payment.TrialConvert`, `payflow.ApplyDeviceLimit`). Панель: вкладка и аудитория «Пробный период» (`users.trial_used_at` и нет `confirmed` тарифа), тег «Пробный» в списке, строка в карточке, карточка настроек.

Рефералка (этап 9, миграция 00016, `core/store/referral.go`, `payflow.PayReferrer`, `bot/internal/referral`, `routes/referral.go`): настройка `referralDays` (0..365, дефолт 0; 0 = выключена, включается в Настройках: кнопки «Пригласить друга» нет, награды не создаются). Ссылка `https://t.me/<бот>?start=ref_<telegramId>` (username бота — `getMe`, кэш в `handlers`). `users.referred_by` пишет только `Store.RecordReferral` из `/start ref_<id>` и только когда строки юзера в `users` ещё нет (LastSeen пишет строку ПОСЛЕ хендлера, так что первое касание видно именно в хендлере; `INSERT … ON CONFLICT DO NOTHING` в одной команде с проверкой пригласившего): свой id, неизвестный пригласивший, мусор, существующий юзер, повторный `/start` с другим payload — ничего не пишут, юзер видит то же приветствие. Запись не зависит от `referralDays`. Награда — таблица `referral_rewards(referred_id PK, referrer_id, days, payment_id, referred_rewarded_at, referrer_rewarded_at)`: не больше одной на приглашённого за всё время. Триггер — `Store.ResolvePaymentRef(…, referralDays, apply)` (его зовёт `payflow.Resolve` из бота и панели, `Decision.ReferralDays`; `ResolvePayment` = то же с 0, им пользуется `payByPromo`) под `lockUserTerm` юзера и блокировкой его строки и платежа: подтверждение, `kind=tariff`, `price > 0` (платёж промокодом на 0 ₽ и докупка устройств не считаются; любая положительная цена считается — минимального порога нет, вопрос в DELAYED.md), у юзера есть `referred_by`, награды ещё нет и нет другого подтверждённого оплаченного тарифа (оплатил первый раз при выключенной рефералке — награды не будет). Тогда `p.ReferralFriendDays` (0, если друг заблокирован админом: он платит как обычно, а пригласивший награду получает) попадает в `apply`, срок друга = `ExtendedExpire + дни` одной записью в панель, в той же транзакции пишутся строка награды, `grants` (`source=referral`) и в outbox `referral_friend` (`referral.friend_bonus`). Отклонение, отмена, ошибка панели откатывают всё. Пригласивший получает дни ПОСЛЕ коммита платежа отдельной транзакцией `Store.GrantReferral` (`payflow.PayReferrer`: под `lockUserTerm` пригласившего, строка награды `FOR UPDATE`, `referrer_rewarded_at IS NULL` проверяется под замком — повторы и параллельные запуски дают `ErrAlreadyRewarded`; заблокированному — `ErrBlocked`, награда остаётся; сдвиг его pending-платежа, панель как у `GrantDays` (`termGrant`), `grants` `source=referral`, outbox `referral_referrer` (`referral.referrer_bonus`)). `p.ReferralPending` говорит вызывающему (`routes.review`, `api resolvePayment`) выдать дни сразу; не вышло (сбой панели, падение между коммитом и выдачей) — cron `*/5` в боте (`referral.Reconciler`, `Store.ReferralsDue`: нет `referrer_rewarded_at` и пригласивший не заблокирован; сбой одной награды откладывается с растущей паузой 5 мин…6 ч в памяти, остальные не голодают); снятая блокировка возвращает награду в выборку сама. В каждой транзакции берётся один пользовательский замок. Пригласивший без юзера в панели получит его через `CreateUser` (без лимита устройств). Карточка: «Пригласил друзей» = `N (оплатили M)`, «Пригласил» (ссылка на карточку) при `referred_by`; `GET /api/users/{id}` отдаёт `referral{invited,paid,referredBy,referredByUsername}`; на экране «Настройки» карточка «Рефералка».

Outbox: все уведомления, не являющиеся ответом на действие юзера (результат проверки, напоминания, рассылка), кладутся в таблицу `outbox(id, event_type, payload)` (payload — jsonb; `payment_result`, `reminder`, `broadcast`, `broadcast_summary`, `direct`, `text_test`, `payment_admin_closed`, `grant_days`, `trial_started`, `referral_friend`, `referral_referrer`, `gift_result`, `gift_redeemed`) и доставляются воркером `internal/outbox`; обработанная строка удаляется. Фото — `Photo` (Telegram `file_id`, старые строки) или `PhotoID` (uuid из `broadcast_photos`): есть → `sendPhoto` с подписью `Text`. Для `PhotoID` воркер берёт `Store.PhotoForSend`: у картинки есть `file_id` → шлёт по нему, нет → первое сообщение уходит байтами (multipart через инструментированного бота), `file_id` самого большого размера из ответа записывается `SetPhotoFileID` (`WHERE file_id IS NULL`, идемпотентно; сбой записи не мешает доставке — следующая строка пошлёт байты ещё раз), остальным получателям фото идёт по `file_id`. Отказ Telegram на загрузке — обычные правила (400/403 дроп, остальное повтор), `file_id` не пишется. Картинки в БД нет (`ErrNotFound`) — строка проваливается (`failed`, error `outbox photo is missing`), текст без фото не уходит. Таблица `broadcast_photos(id, content bytea, content_type, size, file_id, created_at)` и `photo_id` у `broadcasts`/`direct_messages` (миграция 00019, `ON DELETE SET NULL`); `Store.DeleteStalePhotos` (cron бота `30 4 * * *`) удаляет картинки старше 7 дней, на которые не ссылается ни рассылка (в т.ч. черновик и отменённая), ни личное сообщение. Флаг `Template` (есть `{{.x}}` в рассылке, личном сообщении, «Отправить мне»): воркер подставляет общие переменные на получателя при доставке через `content.Provider.Render` (настройки из снимка, не больше одной строки `users` на доставку, значения экранированы); без флага текст уходит как есть — старые строки и обычный текст с «{{». Рассылки и личные сообщения: счётчики и итог живут в БД (`broadcasts(id uuid, idempotency_key UNIQUE, text, photo, total/sent/failed, finished_at)`, `direct_messages(status pending|sent|failed)`; миграция 00005), воркер пишет доставку (`BroadcastDelivered`/`FinishBroadcast`/`DirectDelivered`) и собирает `broadcast_summary` из БД; старые строки без `Broadcast`/`DirectID` доставляются как раньше (строки старой `/a`: `Broadcast` — uuid, которого нет в `broadcasts`, поэтому счётчики не пишутся, а итог — «Рассылка завершена» без цифр); `bot_broadcasts_total` растёт по итогу. `payment_result` пишется в транзакции `ResolvePayment`. Напоминания в `ReminderTimes` (настройка, список `HH:MM` Europe/Moscow: 1..6 без повторов, по возрастанию; старый ключ `reminderTime` читается как список из одного; бот переставляет cron-задачи (по одной на время) без перезапуска, `NOTIFICATION_CRON` — только дефолт: все часы выражения `M h1,h2 * * *` при одной минуте; другое выражение или больше 6 часов → `12:00` + warn): «скоро закончится» (≤`ReminderWeekDays`, дефолт 7 дн.) и «заканчивается» (≤`ReminderDayHours`, дефолт 24 ч), по одному разу на дату окончания; дедуп-ключ `notify:<id>:<expireAt unix>:<week|day>` остаётся в Redis, TTL = первый порог + сутки. Код — `internal/reminder` (отбор/дедуп, кладёт в outbox), текст — `routes.ReminderMessage`.

Подарки (этап 10, миграция 00017, `core/store/gifts.go`, `payflow.RedeemGift`, `routes/gift.go`): `gifts(id, code UNIQUE, months 1..120, status pending|ready|redeemed|cancelled, buyer_id, payment_id UNIQUE, created_by_admin, redeemed_by/at)`, `payments.kind` расширен значением `gift`, `grants.days` до 3650 (подарок на 120 мес.). Код — 128 бит `crypto/rand` в base64url (22 символа, `store.NewGiftCode`), ссылка `https://t.me/<бот>?start=gift_<код>`; username бота берёт воркер (`getMe`, `app.giftNotice`), в outbox лежит только `gift_code`. Два пути: (а) покупка в боте — кнопка «Подарить» (пока в настройках есть тарифы) → тот же список тарифов (`gprice:<мес>`) → «Верно?» → «Да» (`gbuy:<мес>`) создаёт `payments` kind=gift (месяцы и цена тарифа; без промокодов, устройств, аванса, без панели покупателя, `CreatePayment` не читает срок и не заводит юзера) и pending-строку `gifts` в одной транзакции; чужой открытый платёж не отменяется (`ErrPendingExists` → текст `gift.busy`), открытый платёж за подарок отменяется новой оплатой подписки (подарок → cancelled), как и `CancelPayment`. Подтверждение (бот или панель, `payflow.Resolve`): подарок → ready, срок/устройства/лимит покупателя НЕ меняются (`Payment.ExtraAfter` для gift возвращает текущее), outbox `gift_result` (`gift.ready` с ссылкой и кнопкой «Скопировать ссылку»; отклонение — `gift.declined`, подарок cancelled). Оплаченный подарок идёт в выручку и счётчики подтверждённых, но НЕ считается оплатой тарифа: рефералка, «только новым» промокоды, сброс неоплаченных авансов, конвертация пробного, поле «тариф» в списках (всё фильтрует `kind = 'tariff'`), а `trialAllowed` не считает его оплатой (`kind <> 'gift'`). (б) выдача из панели — `Store.CreateAdminGifts` (ready, `created_by_admin`). Активация `/start gift_<код>` (`startPayload`, `login`/`ref_` работают как раньше): `Store.RedeemGift` одной транзакцией — `lockUserTerm(активирующий)` → строка подарка `FOR UPDATE` → статус ready и юзер не заблокирован (иначе `ErrGiftUnavailable`) → сдвиг базы pending-тарифа (как `GrantDays`) → `apply` (панель: `Prepare` заводит нового юзера через `ensureUser` с лимитом устройств из настроек, абсолютный срок `max(панель, now)+месяцы·30 суток` через `termGrant`) → статус redeemed → `grants(source gift)` → outbox `gift_redeemed`: `gift.redeemed` активировавшему и `gift.redeemed_buyer` покупателю (кто активировал, не сообщается; сам себе — одно уведомление). Любой отказ (мусорный/неизвестный/использованный/отменённый/не оплаченный код, блокировка админом) даёт один и тот же текст `gift.unavailable` и один sentinel; код проверяется регэкспом до БД. Ошибка панели откатывает транзакцию (повтор считает ту же дату), сбой коммита после записи в панель возвращает прежний срок (`termGrant.restore`). Блокировка запрещает активацию, но не оплату подарка. Пробный не мешает: подарок только продлевает срок, лимит устройств пробного остаётся. Панель: экран «Подарки» (`/gifts`, `GET /api/gifts?status=all|pending|ready|redeemed|cancelled&page=`, `POST /api/gifts` `{months 1..120, count 1..20}` → 201, `POST /api/gifts/{id}/cancel` (в панели «Отозвать») — только ready: 204/404/409 `not_active`; `DELETE /api/gifts/{id}`, см. «Удаление в админке»), код pending-подарка наружу не отдаётся, ссылка собирается на фронте из `useMe().bot.username`; платёж kind=gift в таблице платежей — тег «Подарок» и диалог «Срок покупателя не изменится».

Рассылки — жизненный цикл (миграция 00011, `core/broadcast`, `Store.SendBroadcast`/`ClaimDue`): `broadcasts.status` = `draft|scheduled|sending|sent|cancelled`. Отправка (`POST /api/broadcasts`) создаёт строку `scheduled` (с `DraftID` — переводит черновик, получающий `idempotency_key`) и, если `scheduled_at` пуст, в той же транзакции запускает её; повтор с тем же ключом возвращает ту же рассылку (200, outbox не трогается, двойной клик на «Отправить позже» — одна строка). Запуск = `startLocked`: аудитория считается из `users` на момент старта (не заблокировавшие бота и не заблокированные админом), `scheduled → sending` (`WHERE status='scheduled'`), `total`, строки outbox получателям и итог админу — одной транзакцией. Планировщик (`bot/internal/broadcast`, компонент `broadcasts`, тик 20 с, на старте догоняет пропущенное): `Store.ClaimDue` берёт по одной `scheduled` с `scheduled_at <= now` через `FOR UPDATE SKIP LOCKED` и запускает в её же транзакции — рестарт или второй воркер не стартуют рассылку дважды. Правка (`PUT /api/broadcasts/{id}`) и отмена (`POST …/cancel`) — только `draft`/`scheduled`: `UPDATE … WHERE status=…` ждёт блокировку строки у `ClaimDue` и перепроверяет статус, поэтому проигравший получает `ErrBroadcastLocked` → 409 `locked` (правка, державшая блокировку, пропускается `SKIP LOCKED` и стартует на следующем тике со своим содержимым). `FinishBroadcast` переводит `sending → sent`. Время из панели — `scheduledAt` строкой `ГГГГ-ММ-ДДTЧЧ:ММ` по Москве (без пояса и секунд, парсинг `ParseInLocation`, DST нет), в БД UTC; не позже «сейчас» — 400. `GET /api/broadcasts?status=a,b&page=` (статусы через запятую; только `scheduled` — по времени старта), `GET /api/broadcasts/{id}`.

Аудитории рассылки (`audience` + `audienceDays`, `core/broadcast`): `all` — каждый юзер из `users`, кроме `blocked_bot_at` (заблокировал бота) и `blocked_at` (заблокирован админом); `active` — `expire_at > now`; `no_subscription` — `expire_at` пуст или `<= now`; `expiring` — `expire_at` в пределах `(now, now + N дней]`, N 1..60 (обязателен только для `expiring`, у остальных — null, иначе 400). Аудитория считается при старте в `startLocked` из той же функции `audienceWhere`, что и счётчики: `GET /api/broadcasts/recipients?days=N` — все аудитории сразу (`expiring` — если N корректно), `?audience=X[&days=N]` — `{count}` одной (диалог подтверждения перезапрашивает её на момент клика). Юзеры, ни разу не нажавшие /start, но попавшие в `users` из панели, получат рассылку; 403 пометит их `blocked_bot_at` позже. «Пробный период» — этап 8.

Кнопки и «Без звука» (только рассылки; личные сообщения без них): `buttons` — до 6 кнопок (`MaxButtons`), в строке до 2 (`MaxRowButtons`), `{text, url, style, inline?}` (в композере кнопки переставляются перетаскиванием тем же `LayoutGrid`, `lib/button-rows.ts` переводит расположение в `inline`): `inline: true` — в строке предыдущей, нет поля — своя строка (так читаются старые рассылки), первая кнопка не inline, третья в строке — отказ (`broadcast.ValidateButtons`, `broadcast.Rows` группирует, `Keyboard` строит ряды): текст 1..64 UTF-16 простым текстом без пробелов по краям и без `{{`, ссылка только `https://` с хостом (≤512, без пробелов/управляющих, без userinfo и opaque: `javascript:`, `data:`, `http:`, `tg:` отклоняются), стиль из `texts.Styles`. Хранятся в `broadcasts.buttons` (jsonb); при старте `broadcast.Keyboard` кладёт inline-клавиатуру (url-кнопки) в payload outbox вместе с `silent` → воркер шлёт `ReplyMarkup` и `DisableNotification` и в `sendMessage`, и в `sendPhoto`. «Отправить себе» (`preview-send`) принимает те же `buttons`/`silent`. Превью композера показывает клавиатуру через `MessageBubble keyboard` (кнопки без href).

Черновики и расписание в композере (`web/admin/src/compose/Composer.tsx`): автосохранение через 1,5 с после правки (`PUT /api/broadcasts/{id}` с uuid, выбранным клиентом: создаёт черновик при первой правке и обновляет его, повтор идемпотентен; запросы идут по цепочке; открытие без правок черновик не создаёт; уход со страницы сбрасывает отложенное). Черновик хранится без проверки содержимого (`normalizeDraft`: границы полей, неизвестная аудитория/время — 400, кривые дни `expiring` не сохраняются), все правила применяются при отправке. Отправка черновика — `POST /api/broadcasts` с `draftId`: ждёт идущее сохранение, гасит отложенное, строка получает ключ и статус (`SaveDraft` после этого → 409). Ключ идемпотентности меняется при любой правке содержимого, аудитории, кнопок, «без звука» и времени; двойной клик с тем же ключом — одна строка (200). Запланированная правится явно («Сохранить изменения» → `PUT`, полная проверка, время обязательно, без автосохранения), ключ при этом не трогается: повтор старого POST вернёт ту же (изменённую) строку, дубля нет. Время — `datetime-local` по Москве (`compose/schedule.ts`, подпись «по московскому времени (UTC+3)»). Экраны: `/broadcasts/new`, `/broadcasts/:id/edit` (черновик или запланированная; запущенная и отменённая — редирект). Вкладки списка — фильтр `status` на сервере: Все / Запланированные (`scheduled`) / Отправленные (`sending,sent`) / Черновики (`draft`).

Данные юзера (`users`, миграция 00007): `first_name`, `last_name`, `last_seen_at` — пишет `middleware.LastSeen` после хендлера (сообщение в личке или кнопка; upsert, так что в таблице и те, кто только нажал /start; не чаще раза в 5 минут на юзера в памяти процесса; сбой только в лог) и заодно снимает `blocked_bot_at`. `expire_at`, `panel_status` (`NULL` — нет в панели), `synced_at` — копия панели: `core/panelsync.Run` читает панель целиком (сбой или пустой ответ → `ErrPanel`, ничего не записано), затем одной транзакцией `Store.ApplyPanelSync` заводит новых юзеров, снимает статус с исчезнувших из панели, запоминает итог в `panel_sync`; строки с `synced_at` позже начала прохода свежее снимка и не трогаются. Запуск: cron бота каждые 15 минут (сбой → лог + `bot_panel_sync_failures_total`) и `POST /api/sync`; не пересекаются через `Store.WithPanelSyncLock` (`pg_try_advisory_lock`, занято → `ErrSyncRunning`). Запись сразу после вызова панели: декоратор `routes.writeThrough` в `Register` (`CreateUser`/`UpdateUser` любого хендлера) → `Store.SetUserPanel`, строку под блокировкой пропускает (`SKIP LOCKED`: `CreatePayment` держит её, пока ждёт панель; ожидание было бы дедлоком), пропуск дочинит синхронизация. `blocked_bot_at` ставит outbox-воркер на 403 (первое время сохраняется), `broadcasts_received` растит на доставке `broadcast` (после удаления строки: повтор отправки не удваивает, падение между удалением и записью теряет отметку). `blocked_at` пока не используется (этап 6). Имя в админке: главная подпись юзера везде (список, карточка и `usePageTitle`, платежи, активации, подарки, «Пригласил», пикеры) — `userLabel` (`web/admin/src/promo.ts`): `name` (имя+фамилия), иначе `@username`, иначе `ID n`; вторая строка — `userSub` (то, чего нет в подписи: `@тег · ID n` под именем, `ID n` под `@тегом`, под `ID n` пусто), тег-ссылка `https://t.me/<username>` (`userTagUrl`, только при непустом username, `_blank noopener`), в карточке ID копируется кнопкой (тост «ID скопирован»). API отдаёт `name` в платежах (`paymentCols`, подзапрос к `users`), активациях, `buyerName`/`redeemedName` подарков, `referral.referredByName`. Добор имён: бот (`bot/internal/names`, cron `*/10` и один проход при старте) берёт `Store.NamesDue` (имя и фамилия пусты, `name_checked_at` NULL либо старше 7 дней, свежие `last_seen_at` первыми, ≤25), спрашивает `getChat` через инструментированный клиент с паузой 100 мс и пишет `Store.SaveChatName` (миграция 00018, `users.name_checked_at`): пустое значение имеющееся не стирает, новый непустой username заменяет прежний. 400/403/404 от Telegram (чата нет) тоже отмечаются проверкой (повтор через неделю), 429 прерывает проход без отметки, сетевой сбой — без отметки, идём дальше. Юзер, написавший боту, обновляется `LastSeen` как раньше; `ApplyPanelSync` имя и username существующих строк не трогает.

Глобальные переменные: в любом тексте реестра (сообщение, кнопка, простой) доступны общие — системные `{{.name}}`, `{{.username}}`, `{{.telegramId}}`, `{{.expireAt}}` (МСК, нет значения — «—»), `{{.phone}}`, `{{.bank}}`, `{{.supportUrl}}` и свои из `Settings.Vars` (ключ `vars`: имя `^[a-zA-Z][a-zA-Z0-9_]*$`, не занято (`texts.Reserved`), значение до 96 символов (`texts.MaxCustomVar`, UTF-16; проверяется только при `PUT /api/settings` через `ValidateForSave` — `Validate` при загрузке длину не смотрит, чтобы сохранённые длиннее 96 не сбрасывали бота на env-дефолты; `GET /api/settings` отдаёт их в `problems` без `usingDefaults`, панель просит сократить и не даёт сохранить), экранируется как обычная переменная). С переменными текстов (`Def.Vars`) имена не пересекаются — тест реестра. Значения собирает единственное место — `content.Provider`: настройки из одного снимка с телом текста, получатель из контекста: `middleware.TextUser` кладёт автора апдейта (`content.WithUser`), для другого адресата — `content.ForUser(ctx, id)` (админ решает платёж, напоминание, outbox). `users` читается одной строкой (`Store.UserContact`) и только если тело просит то, чего нет в контексте. Значение от вызывающего важнее (`expireAt` — только что посчитанный срок). Неизвестная переменная рендерится пустой, а при загрузке (`ValidateStored`) не отменяет правку; весь текст пуст → текст по умолчанию (Telegram отверг бы). При сохранении `Validate` строг: неизвестная и неразборчивая (`{{name}}`, `{{.a b}}`) → 400; длина по худшему случаю (`Var.Max`, свои — 96, сохранённое длиннее считается по факту). Кнопки и простые тексты (лимит 64 UTF-16, `maxButtonLen`) при рендере не обрезаются: `Validate` считает худший случай (общие и свои переменные текста — `Var.Max`, свои общие — по ТЕКУЩЕМУ значению) и при превышении отдаёт 400 «{{.name}} может не влезть в кнопку: до 64 символов» (называет самую длинную переменную; `{{.name}}` в одиночку — ровно 64 — проходит, `telegramId`/`expireAt` коротки). Последняя страховка в `content.Provider.Text`: пустая подпись или длиннее 64 (`texts.FitsPlain`; например значение переменной поменяли в БД в обход API) → текст по умолчанию + warn один раз на ключ, никогда не пусто и не длиннее лимита; сохранённая правка, переставшая проходить `ValidateStored`, и так отбрасывается до дефолта. Удалить свою переменную из сохранённого текста нельзя, а изменить её значение так, чтобы сохранённая кнопка или простой текст перестали влезать, тоже: `PUT /api/settings` → 400 с ключами текстов.

## Удаление в админке (миграция 00020)

- **Рассылки**: `DELETE /api/broadcasts/{id}` — `draft|scheduled|cancelled`, 204. `Store.DeleteBroadcast`: `FOR UPDATE` строки (ждёт `ClaimDue`, который её уже стартует), статус перепроверяется: `sending|sent` — история со счётчиками → 409 `not_deletable` (стартовавшая в гонке тоже получает его, а не `locked`); нет — 404. У не стартовавшей нет строк outbox; картинка без ссылок уйдёт ночной чисткой (`DeleteStalePhotos`). «Отменить» (запланированную) остаётся: не отправлять, но оставить в истории как `cancelled`; «Удалить» убирает строку совсем. Автосохранение композера после удаления может пересоздать черновик, если запрос был в полёте (уход со страницы сбрасывает отложенное).
- **Промокоды**: `DELETE /api/promos/{id}`, 204, повтор безвреден, 404 неизвестный. `Store.DeletePromo` под `FOR UPDATE` строки кода (как активация и `CreatePayment`): нет ни `promo_activations`, ни `payments.promo_id` → физически (код можно создать снова); иначе `promo_codes.deleted_at` — код остаётся занятым (UNIQUE), скрыт из `status=all|active|expired|disabled`, виден в `status=deleted` (вкладка «Удалённые», `Promo.deleted`), активации и коды в платежах целы, `used` не меняется. Бот: `PromoByCode` не находит удалённый (`promo.not_found`), `checkPromoLocked` → `promo.ErrNotFound`, `promo.Check` держит `Deleted` как `Disabled`. Уже созданный платёж со скидкой подтверждается как раньше. `enable`/`disable` удалённого — 404.
- **Подарки**: действие панели `POST /api/gifts/{id}/cancel` в интерфейсе называется «Отозвать» (вкладка «Отозванные», статус в БД по-прежнему `cancelled`): работает только для `ready`, ссылка перестаёт работать, а у уже активированного подарка (`redeemed`) срок получателя НЕ меняется и отозвать его нельзя. `DELETE /api/gifts/{id}` — `ready` (отзыв и удаление одним шагом) и `cancelled`; подарок админа (нет `payment_id`) стирается физически, купленный остаётся строкой `cancelled` с `deleted_at` (след денег, связь с платежом) и скрыт из `GET /api/gifts`. `pending` и `redeemed` — 409 `not_deletable` (оплата в ходу, `grants`). `Store.DeleteGift` под `FOR UPDATE` строки, как `RedeemGift`: параллельная активация либо выигрывает (тогда 409), либо видит отозванный/стёртый подарок (`ErrGiftUnavailable`). Повтор на удалённом — 204.
- Все три `DELETE` — мутирующие: сессия (401), только `application/json` (415). Фронт: общий `DeleteDialog` (`pages/delete-dialog.tsx`, один запрос на нажатие, 404 = уже удалено, 409 = строка устарела).

Раскладка клавиатур («в коде логика, в панели вид»; `core/texts/keyboards.go`, миграция 00021 `text_keyboards(keyboard_id PK, rows jsonb, hidden jsonb)`, `Store.KeyboardLayouts|SaveKeyboardLayout|DeleteKeyboardLayout`): код решает, какие кнопки есть, их условия, callback/URL и подписи; админ — порядок, ряды (до `MaxRowSlots`=2 кнопок, до `MaxRows`=8 рядов), стиль и подпись (как и раньше, через `PUT /api/texts/{buttonKey}`, они общие для кнопки на всех экранах) и скрытие «за ненадобностью». Единица — клавиатура `texts.Keyboard{ID, Title, Messages, Slots, Blocks, Default}`, а не сообщение: одна клавиатура стоит под многими сообщениями (`menu`/`menu_new` — главное меню под приветствием и всеми уведомлениями), у сообщения их может быть несколько (`menu.greeting` — юзер в панели и нет). Слот — ключ кнопки реестра (`Slot.Removable`: true только у необязательных действий меню, «Продлить», «Подписка», «Поддержка», «Есть промокод», «Без доп. устройств», «Промокод», «Пробный», «Устройства», «Подарить», «Пригласить друга»; false у Да/Нет/Назад, «Купить», «Скопировать ссылку», «Убрать промокод» — без них сценарий упирается в тупик) или динамический блок `@tariffs`/`@devices` (кнопки, число которых решает код: двигается, не скрывается, в ряду один, раскрывается своими рядами по 2). Расположение по умолчанию (`Default`) — побайтно то, что бот строил до раскладок (золотой тест `routes/keyboards_golden_test.go`, файл `testdata/keyboards.golden`, `-args -update` только при намеренной смене). `Keyboard.ValidateLayout` — единственная проверка (API при сохранении, `content.Provider` при загрузке: невалидная раскладка отбрасывается с одним warn на клавиатуру, бот на `Default`); `Keyboard.Effective(stored)` — действующие ряды без скрытых, объявленные кнопки, которых нет в сохранённой раскладке (появились в коде позже), встают отдельными рядами в конец в порядке `Default`; `texts.Arrange` расставляет построенное кодом по `Effective`: не построенное (условие не выполнено) отсутствует, раскладка кнопку не навязывает; все скрыты — `markup()` вернёт nil (сообщение без клавиатуры). В боте — `kbBuilder` (`routes/buttons.go`): `newKB(ctx, c, "menu").callback(key, data, style)…url|copy|block(id, rows).markup()`; то же для очереди (`PaymentNotice`, `GiftNotice`, `ReminderMessage` читают раскладку из того же снимка, что и тексты). API: `GET /api/texts` у сообщения отдаёт `keyboards: [{id,title,messages,slots:[{id,kind button|dynamic,label,removable,style}],rows,hidden,default,overridden,dynamic:[{id,title}],inactive,problem}]` (подписи и стили — действующие, для превью), `PUT /api/keyboards/{id}` `{rows, hidden}` → 204 / 400 `invalid` с русским `message` (хранится канонически: в рядах только видимые; раскладка, равная `Default`, не хранится), `DELETE /api/keyboards/{id}` — сброс. Не входят: одиночная «Назад» под сообщением (промокод, пробный недоступен, `*.busy`, `gift.unavailable`, `menu.service_down`), админские кнопки (`adm_ok`/`adm_no`, ссылка входа). Новая кнопка на зарегистрированном экране: ключ в реестре текстов (`btn(...).on(...)`, `Def.Buttons` сообщения), `Slot` в `keyboards` + в `Default` (тест `TestKeyboardRegistry`), строка в `newKB(...)` с условием в коде, обновить золотой файл. Новый экран с несколькими кнопками: `Keyboard` + сообщения в `Messages` + `newKB`; динамический блок — `blocks` и `.block(id, rows)`.

Конструктор клавиатур (заменил общие раскладки выше: `PUT|DELETE /api/keyboards/{id}` и `keyboards[]` в `GET /api/texts` из api удалены; старые раскладки читает только бот как запасной путь и `MigrateLegacyKeyboards`). Клавиатура принадлежит СООБЩЕНИЮ (ключ текста), таблица `message_keyboards(text_key PK, rows jsonb, updated_at)` (миграция 00022); нет строки — клавиатура по умолчанию из кода (`texts.MessageDefault(key)`, строится из `texts.Keyboard.Default`; `menu`+`menu_new` склеены в одну 8-рядную клавиатуру для `menu.greeting` и всех «меню-сообщений»: кнопки, различающиеся по юзеру, разведены условием `in_panel`, дубли `promo_new`/`support_new`; отфильтрованная условием она равна каждой из двух). Золотой тест `routes/keyboards_golden_test.go` проходит на коде (`TestKeyboardsGolden`) и на «сохранённых» умолчаниях конструктора (`TestKeyboardsGoldenViaConstructor`) — оба на одном файле. Ячейка `texts.Cell{id, key?, label?, style?, action, conditions:[{id,not}]}`: `key` — кнопка реестра, чья подпись/стиль действуют, пока свои (`label`/`style`) пусты (правка в «Редакторе сообщений» доходит до такой кнопки; `style` пуст — `texts.style` или стиль на этом экране из кода); у новой кнопки `key` пуст и `label` обязателен (до 64 UTF-16 по худшему случаю с общими и своими переменными, `texts.Validate` для кнопки). Условия (`texts.Conditions`, каталог ровно из того, что бот реально проверяет; вычисляет `routes/conditions.go: condEnv`, юзер панели и пробный — лениво и один раз, не заданное экраном — ложь): `in_panel`, `trial_available`, `devices_sale_on`, `gifts_on`, `referral_on`; несколько — И, у каждого `not`. Действия (`texts.Actions`, allow-list; в боте `routeData`/`argKey`/`templateBlock`, тест `TestConstructorCatalogsImplemented`): `route:<menu|info|pay|promo|devices|trial|gift|referral>` (у devices/trial/gift/referral есть встроенное ограничение `Guard` — условие выше, которое неотключаемо И-ится с условиями админа: «Пробный» выключенный в настройках не показать), `link:support` (ссылка из настроек), `url:<https>` (`texts.ValidHTTPSURL`, общая с кнопками рассылки), привязанные к экрану (`Bound`: `flow:yes|no|have_promo|drop_devices|remove_promo` — данные месяца/тарифа знает экран, `copy:subscription|referral_link|gift_link`, `template:tariffs|gift_tariffs|devices`) — только там, где они есть в клавиатуре по умолчанию, и только на ячейке с тем же id, не больше одной. Служебные ячейки (`locked`: Да/Нет/Назад/Купить/Скопировать ссылку/Убрать промокод и шаблоны) нельзя убрать и менять им действие и условия (подпись, стиль, место — можно). Шаблон — ячейка `template:*` одна в ряду без подписи/стиля/условий. Лимиты: ≤2 в ряду, ≤8 рядов, ≤16 ячеек (`texts.ValidateMessageLayout(key, l, customVars, strict)`: единственная проверка; API зовёт strict, `content.Provider` при загрузке — нестрого, без лимитов рядов/ячеек, чтобы перенесённые из старых раскладок не терялись); противоречия (`id` и `НЕ id`, `НЕ` встроенного условия действия), неизвестные id/условия/действия, повторы id — отказ с русским `message` (`usererr`). Бот: `kbBuilder` (`newKB(ctx, c, id, key)` — `id` клавиатура по умолчанию, `key` сообщение; `h.kb(ctx, id, key)` для экранов с юзером панели, `known`/`inPanel` для мест, где он уже прочитан) строит кнопки как раньше и копит данные экрана (`args`), а при сохранённой клавиатуре сообщения (`Provider.MessageLayout`, снимок как у текстов; невалидная — клавиатура по умолчанию + один warn на пару сообщение/клавиатура) собирает ряды из ячеек: условия → действие → подпись (`Provider.Label`: общие переменные, лимит 64, пусто — «•») → стиль; не получившееся (условие, ограничение, экран не передал данные) пропускается, пустой ряд исчезает, все пропали — сообщение без клавиатуры. Очередь (`PaymentNotice`, `GiftNotice`, `ReminderMessage`, `mainKeyboard(…, key, …)`) читает ту же раскладку по `TextKey`. API: `GET /api/texts` → `items[].keyboard` = `{rows, default, overridden, locked:[id], inactive, problem?}` (null — под сообщением кнопок нет; ячейка = `Cell` + `locked`, `template`, `effective:{label (своя или тело текста кнопки с переменными), preview (на примерах), style}`) и верхние каталоги `conditions:[{id,title,description}]`, `actions:[{id,title,kind,guard?,bound}]`, `templates:[{id,title}]`; `PUT /api/texts/{key}/keyboard` `{rows:[[Cell]]}` → 204 / 400 `invalid` с русским `message` / 404 (нет сообщения или кнопок под ним); раскладка, равная умолчанию, не хранится; `DELETE /api/texts/{key}/keyboard` → 204 (сброс). Миграция старых данных: `Store.MigrateLegacyKeyboards` (зовёт `bot migrate` после goose) переносит строки `text_keyboards` в `message_keyboards` по сообщениям (`texts.LegacyToLayout`: главное меню — ряды `menu` с `in_panel`, затем ряды `menu_new` с `НЕ in_panel`; у сообщения с уже своей клавиатурой не затирает) и удаляет перенесённые старые строки в той же транзакции (повтор — no-op, сброшенное не воскресает); `00021` в `main` не был, так что на проде переносить нечего. Широковещательные кнопки рассылок конструктор не меняет. Новая клавиатура/кнопка: `Keyboard` в `keyboards.go` (умолчание), `cellSpec` (действие, стиль), `newKB(…, key)` с данными экрана; новое действие — в `texts.actions`, `routeData`/`argKey`; новое условие — в `texts.conditions` и `condEnv.eval` (тест `TestConditionEvaluators`).

Редактор клавиатур в панели (`/texts`, `pages/message-keyboard.tsx`, `lib/message-keyboard.ts`): под сообщением с кнопками — карточка «Клавиатура» из `items[].keyboard`; секции «Кнопки» и окна «Системные кнопки» нет, кнопки реестра в списке не показываются. Сетка на `LayoutGrid` (`ui/layout-grid.tsx`, @dnd-kit; правила — `moveSlot`, id ячейки = id в раскладке, шаблоны — блоки на ряд) до 2 ячеек в ряду, ≤8 рядов, ≤16 ячеек. Ячейка: ручка, id и действие моно-строкой, «×» (убрать; у служебных замок), поле подписи (пусто — действует `effective.preview`), `StyleSelect`, кнопки «Действие» (Sheet: `Select` из каталога + свой https-адрес; `bound`-действия не выбираются) и «Условия» (Sheet: чекбоксы каталога и «НЕ»). «+ Кнопка» (новая со своим id `btn_N`, действие `route:menu`), `Select` «+ Шаблон» (по одному). Под превью — чекбоксы «Условия для превью» (условия клавиатуры и встроенные `guard` действий): превью показывает только кнопки, у которых выполнены все условия. «Сохранить клавиатуру» — `PUT /api/texts/{key}/keyboard` и перезагрузка `GET /api/texts`; «Вернуть как в коде» — Dialog и `DELETE`. Все выпадающие списки — `ui/select.tsx` (в стиле `StyleSelect`), нативный `<select>` не использовать.

UX-карта бота (`/map`, «Схема бота» в разделе «Бот», `pages/UxMap.tsx`, `lib/uxmap.ts`): граф экранов и переходов на @xyflow/react + @dagrejs/dagre (раскладка слева направо). Узлы — сообщения реестра (`kind=message`) в виде пузыря с текстом на примерах и клавиатурой, как её применяет бот (`items[].keyboard.rows` из `GET /api/texts`), и входы (команды `/start`, `/login`, `/start gift_…`, фото платежа; события админа и системы). Стрелка кнопки выходит из точки на самой кнопке; пунктир — переход без кнопки (ввод юзера, решение админа, событие). Куда ведёт кнопка, описано таблицами в `core/texts/uxmap.go` (`GET /api/uxmap`: `entries`, `transitions` по `(экран, действие)` с общим `*` для `route:*`, `links`); тесты `core/texts/uxmap_test.go` падают, если появился экран без пути к нему, ссылка на несуществующий экран или кнопка клавиатуры по умолчанию без записи в таблице, — **новый экран или кнопку нужно описать в `uxmap.go`**. Сверху «Условия для превью» (только встречающиеся в клавиатурах; скрывают кнопки и их стрелки) и чипы групп (фильтр экранов). «Править» в узле открывает сообщение в редакторе.

Контраст (F4): активный пункт меню (сайдбар) и текста — `bg-accent-strong text-on-accent-strong`, активная вкладка телефона — `text-accent-strong`; пары ≥ 4.5:1 в обеих темах проверяет `web/admin/src/styles/contrast.test.ts` по `design/tokens.json`.

Вход: `/login` в боте (или deep link `?start=login` со страницы входа: `/start login` от админа вызывает тот же `login`, от остальных — обычное приветствие, без токена и намёка) → inline-кнопка со ссылкой `ADMIN_BASE_URL/auth?token=…` (токен одноразовый, 5 мин; ссылка только в кнопке, превью отключено) → сессионная cookie `bn_session` на 24 ч. Тексты входа — в реестре (группа «Вход»): `login.message` с клавиатурой из конструктора (ячейка `button.login`, служебная, действие `link:login` — ссылка с токеном подставляется кодом, подпись и стиль правятся в редакторе), `login.fallback` (целое сообщение вместо `login.message`, когда Telegram не принял URL-кнопку: переменная `{{.link}}` — ссылка с токеном, её место в тексте админ выбирает сам; в dev так бывает с `localhost`: Telegram не принимает его в URL-кнопке. Чтобы в dev приходила настоящая кнопка, задай `ADMIN_BASE_URL=http://admin.localtest.me:5173` (домен резолвится в 127.0.0.1) и добавь в `web/admin/vite.config.ts` `server.allowedHosts: ['.localtest.me']`); токен и ссылка по-прежнему только в кнопке/блоке `<code>`, превью выключено. `/api/*` — default-deny: без сессии 401, мутирующие принимают только `application/json`. Админ один — `TELEGRAM_ADMIN_ID`.

Деплой: один образ (bot + api + фронт), compose-сервис `api` (`/app/api`) слушает `127.0.0.1:8090`; наружу — nginx `admin.bruhanet.ru` → `127.0.0.1:8090` (см. README). Prometheus скрейпит `api:8091`. Токен в `/auth?token=…` попадает в access-лог nginx — безвредно (одноразовый), при желании `access_log off` для `location = /auth`.

**SQL только в `core/store`** — api и bot ходят в БД через него.

**Срок юзера и порядок блокировок.** `CreatePayment`, `GrantDays`, `ActivateDaysPromo` первым оператором транзакции берут `pg_advisory_xact_lock(hashtextextended('user_term:'||current_schema()||':'||telegram_id, 0))` (`lockUserTerm`): выдача дней и создание платежа одного юзера идут строго друг за другом. `CreatePayment` берёт `PrevExpireAt` уже под замком: у отменяемого pending — из него (выдачи, прошедшие раньше, уже сдвинули его), иначе через `readPrev` (бот читает срок в панели, `CreateUser` заводит юзера), а не до транзакции. Порядок везде: advisory → `users` → `payments` → строка промокода. `ResolvePayment`/`GrantAdvance` advisory не берут (не ждут). Строку `users` в `GrantDays` не лочим (`SetUserPanel` SKIP LOCKED). Запланированные рассылки: сбой `startLocked` одной не держит очередь (`ClaimDue` пропускает её в проходе, после 3 сбоев подряд в памяти процесса — `cancelled`).

## Деплой этапа 1 (Postgres)

Деплой этой ветки идёт без живых проверок: до мержа на VPS добавить `POSTGRES_PASSWORD` в `.env` (или прогнать `install.sh` — допишет недостающие ключи); CI-шаг `Check .env keys` упадёт, если ключа нет. Платежи, оставшиеся «на проверке» в Redis FSM, в Postgres не переезжают — бот при старте пишет warn `legacy fsm payment found` с `telegram_id`, разобрать вручную до мержа.

## Команды

`task` — список. Весь dev-стек одной командой — `task stack` (postgres + redis в docker, миграции, затем бот, api и vite в одном терминале с префиксами `[bot] [api] [web]`; Ctrl+C останавливает приложения, контейнеры остаются; `scripts/dev-stack.sh`). Основное: `task setup`, `task up` (Postgres и Redis в docker), `task dev SVC=bot` (air + jq), `task run SVC=bot`, `task test`, `task test:db` (SQL-тесты `store` на dev-Postgres, нужен `task up`), `task migrate` (`bot migrate`; `task run`/`task dev` делают это первым шагом), `task lint`, `task fmt`, `task tidy`. Фронт: `task web:install|dev|build|test|lint` (dev-сервер проксирует `/api` и `/auth` на :8090); api локально — `go -C api run ./cmd` (нужен `NOTIFICATION_CRON` — задай в окружении или подгрузи `.env`; он лишь дефолт времён напоминаний: формат `M h1,h2 * * *`, не больше 6 часов, иначе 12:00 + warn).
Образ (bot + api + фронт, без ENTRYPOINT — команда задаётся в compose): `task docker:build` (TAG=local). Прод-стек: `task deploy:config|up|down|pull|ps`, `task deploy:logs -- <service>` (нужен `deploy/.env`, `BOT_IMAGE_TAG=local task deploy:up` для локального образа). Docker healthcheck бота — `/app/bot healthcheck`, api — `/app/api healthcheck` (liveness `/healthz`, readiness не влияет).
Установка/обновление на VPS: `curl -fsSL https://raw.githubusercontent.com/bruhabruh/bruhanet-bot/main/install.sh | bash` (`install.sh` в корне: качает `deploy/`, спрашивает `.env` по `.env.example`, `pull` + `up -d`; существующий `.env` не трогает; env: `BRUHANET_DIR|REF|TARBALL|INPUT|SKIP_UP`).
CI/CD — `.github/workflows/ci.yaml`: lint + test (pkg, core, bot, api) + web (typecheck, lint, test) + build образа на PR и push в `main`; на push в `main` — push в ghcr (`latest`, `sha-<short>`) и деплой по ssh (секреты environment `production`: `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS`, `SSH_HOST`, `SSH_USER`, `WORK_DIR` — абсолютный путь): копирует `deploy/` без `.env`, `pull` + `up -d` с `BOT_IMAGE_TAG=sha-<short>`, ждёт `State.Health.Status == healthy` у bot и api до 90 с, иначе логи migrate/bot/api и fail, `docker image prune -f` (не `-a` — на VPS ещё Remnawave). Порядок деплоя: проверка ключей `.env` (по `deploy/.env.example` раннера) → копирование `deploy/`, так что провал проверки не трогает VPS. Откат — только перезапуском старого деплоя в CI (он вернёт старый `deploy/`), не через `BOT_IMAGE_TAG=… up`: старый образ с ENTRYPOINT сломает команды api/migrate. Grafana по умолчанию на `127.0.0.1:3030` (3000 занят панелью Remnawave).
После CI-деплоя изменения в bind-mount конфигах `prometheus/`, `tempo/`, `loki/`, `alloy/` подхватываются только через `docker compose restart <service>`.
Новый модуль добавлять в `SERVICES` в `Taskfile.yaml` и в matrix в `ci.yaml`.
Redis-реализация FSM тестируется на miniredis, SQL-тесты `store` пропускаются без `TEST_DATABASE_URL` — docker для `task test` не нужен. Хендлеры тестируются через `tgtest` (`bot.WithSkipGetMe` + `WithServerURL` + `WithNotAsyncHandlers`, апдейты через `ProcessUpdate`).

## Конвенции и подводные камни

- Go **1.27**: есть generic-методы, stdlib `uuid`, `errors.AsType`. Не «чинить» их как ошибки. Но generic-метод не реализует метод интерфейса — поэтому `pkg/remnawave` с `int64`.
- UUID — везде `github.com/google/uuid`, не stdlib: его требуют типы `remnawave-api-go`.
- Ошибки: sentinel в `errors.go` пакета, оборачивать через `errors.Join(ErrX, err)`; проверять `errors.Is`.
- Конфиг: только env-теги `caarlos0/env` + `validate`. Новый env — сразу и в `.env.example`.
- Логи: `slog`, контекстный логгер через `stlog.With/L(ctx)`; поля snake_case.
- Линтер строгий (`.golangci.yml`: gosec, errorlint, exhaustive, gocritic…), формат gofumpt + goimports с local-prefix `github.com/bruhabruh/bruhanet`.
- Язык ошибок: всё, что видит разработчик (значения `error`, sentinel, сообщения и поля `slog`, `panic`, ошибки `pkg/*`), — английский, `fmt.Errorf("…: %w", err)`, строчная первая буква. Русский — только для человека (реестр `core/texts`, тексты админу, `message`/`problems` в ответах API). Ошибка, дошедшая до человека, получает русский текст на границе: если русский текст рождается в `core` (валидация), ошибка создаётся `usererr.Errorf(en, ru, args…)` (`Error()` — английский, `Message()` — русский), API показывает `usererr.Message(err)`/`texts.Problem(err)`; `err.Error()` человеку не отдаём. Страж — `core/langguard` (тест, входит в `go test` core): падает на кириллице в `errors.New`/`fmt.Errorf`/`errors.Join`/`slog`-вызовах/`panic`/`Error()` вне тестов; единственные выходы — второй аргумент `usererr.Errorf` и комментарий `//lang:ru` на строке вызова или строкой выше (держать список крошечным; сейчас таких мест нет).
- Стиль текстов (миграция 00023 сбросила все сохранённые правки `texts`): на «ты», коротко, 1–2 эмодзи на сообщение, жирным заголовок и ключевые значения (срок, сумма), реквизиты шагами; экраны подтверждения — «Проверь заказ», не «Выбор тарифа». Тексты юзеру на русском, parse mode HTML (`models.ParseModeHTML`). Новый текст юзеру — только через реестр `core/texts` (`Default` = точный текст), рендер только `texts.RenderDef` (экранирует не-Raw переменные); читать через `Content` (`bot/internal/content`); текст другому юзеру, не автору апдейта, — с `content.ForUser(ctx, id)`. Тексты админу — в коде, динамическое через `html.EscapeString`. Плюрализация «месяц/месяца/месяцев».
- Имена файлов — нижний регистр через `_` (`in_memory.go`).
- `MatchFunc` go-telegram выполняется синхронно до всех middleware: только проверки полей, без I/O и паник.
- Роуты регистрируются только в `handler/routes/routes.go` (`Register`), хендлер роута — в своём файле `handler/routes/<route>.go`. Статичная кнопка — `keyboard.Callback(text, "pay")`; с аргументом — `var Price = callback.New[int]("price")`, кнопка `keyboard.Callback(text, Price.Data(6))`, в хендлере `Price.Parse(u.CallbackQuery.Data)`. Callback data подделывается клиентом — аргумент валидировать (тариф есть в `Content.Settings(ctx).Prices`), админские роуты — с `middleware.AdminOnly`.
- Внешние вызовы — только через инструментированные клиенты (Remnawave-декоратор `InstrumentRemnawave`, `TelegramTransport`, Redis-хук); пробы зависимостей — через `observability.WithProbe` или необорачиваемый клиент. telegram_id/request_id/error в метки метрик не класть.
- SQL — только в `core/store`. Миграции — отдельный one-shot `bot migrate` (в проде сервис `migrate`, бот стартует после него); `app.New` лишь делает `CheckSchema` (есть непримененные → `ErrSchemaOutdated`, бот не стартует). Уведомление, не являющееся ответом на действие (результат проверки, напоминание, рассылка), — только через outbox.
- Стили кнопок — только `keyboard.Style*` константы. Кнопка с подписью из реестра строится через `callbackButton|urlButton|copyButton` (`routes/buttons.go`): стиль из аргумента — вид на этом экране, пока админ не сохранил свой в `texts.style` (nullable, миграция 00008; `body` там же nullable: изменён только стиль). Сохранён вид по умолчанию (`Def.Style`) — снова `NULL`, на других экранах у кнопки опять их вид из кода. `DELETE /api/texts/{key}` сбрасывает и подпись, и стиль. Новая кнопка на экране — и в `Def.Buttons` этого сообщения (тест `TestDeclaredButtons`).
- На callback отвечать через `middleware.Answer`, или повесить на роут `middleware.AutoAnswer("текст")` (toast после хендлера); иначе глобальный `AutoAnswer()` ответит пустым.
- Служебное состояние апдейта (route, answered, panicked) — `middleware.UpdateInfoFrom(ctx)`; это не логирование.
- Дизайн каркаса хендлеров: `docs/superpowers/specs/2026-10-26-bot-handler-infra-design.md`.
- Callback data в старом боте — короткие коды `"0".."5"` + `:<arg>` (лимит Telegram 64 байта).
- Грабли старого кода, не повторять: обращение к `payment.*` до проверки `err` (nil-паника), повторное нажатие Подтвердить/Отклонить, игнор ошибок `UpdateUser` при выдаче 1 дня, admin-хендлеры без проверки `AdminID`.
- Экраны по callback — `show` (редактирование на месте, fallback — новое сообщение); ответы на фото/текст — `send`.
- Remnawave в хендлерах — только через `routes.Remnawave`; в тестах `tgtest.NewRemnawave`. Время — `h.now()` (поле `handlers.now`).
- Message-роуты роутера матчатся в порядке регистрации в `routes.Register` (= приоритет). Рассылки и личные сообщения — только из веб-админки (api кладёт в outbox); команды `/a` в боте нет — от админа это обычное сообщение (меню).

## Фикс-волна после ревью (этап 7–9)

- **Платёж промокодом на 0 ₽ (`payByPromo`)**: лимит устройств (`ApplyDeviceLimit`, идемпотентный) пишется ДО срока (`UpdateUser`). Любой сбой после записи срока (коммит, отказ БД по коду под блокировкой) возвращает прежний срок `payflow.RestoreTerm` (`PrevExpireAt`, только пока в панели всё ещё наше значение; `ErrNotRestored` в логе), иначе повтор прочёл бы продлённый срок как прежний и продлил ещё раз. `payflow.Resolve` (решение админа) в такой защите не нуждается: запись абсолютная от `PrevExpireAt`, повтор считает ту же дату.
- **Подарок**: строка `gift_result`/`gift.ready` в outbox не снимается по `maxAttempts` при временных сбоях (getMe, сеть, 5xx): повтор с backoff, error `gift link still not delivered` с `gift_code` каждые `maxAttempts` попыток. Снимается только при окончательном отказе Telegram (400/403) с error `gift link not delivered` и `gift_code` (код виден в списке подарков админки). `giftNotice` не держит мьютекс на время `getMe`.
- **`CreatePayment`**: новый тариф не отменяет pending докупки устройств/подарка с отправленным чеком (`SubmittedAt != nil`) — `ErrPendingExists`, бот показывает `devices.busy`/`gift.busy` по виду открытого платежа; неотправленные докупка/подарок и любой pending-тариф отменяются, как раньше. `GrantAdvance` для не-тарифа даёт `ErrNotPending`.
- **Метрики**: метка `months` у `bot_payments_total`/`bot_payments_confirmed_rubles_total` для докупки и подарка — `devices`/`gift` (`observability.PaymentLabel`; `OutboxMessage.PayKind` для решения из панели).
